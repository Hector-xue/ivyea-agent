## 0. 摘要

### 0.1 一句话

**IvyeaAgent 内核只持有插件契约，别的什么都不持有。**
工具、技能、知识、Web 界面、IvyeaOps 板块——全部是插件。
契约本身对齐业界正在收敛的**协议型**事实标准，因此第三方用任何语言都能写插件，
且我们的技能反过来能被 Claude Code / Codex / DeepSeek Harness 直接使用。

### 0.2 v1 错在哪（必读，否则会重蹈）

v1 的根本错误是**把"兼容别人的生态"理解成"寄生进别人的运行时"**。

沿着那条路推下去，结论必然是"引入 Cordis + `@deepseek-ai/*` 包 + Node 边车"，
于是变成"怎么让别人的容器收留我们"，而不是"我们的契约怎么定"。
这是 v1 读起来像退而求其次的根因——它确实是。

推翻它的是两个实证发现：

**① 插件生态有两种，代价差一个数量级**

| | **代码型**（DeepSeek Harness / Cordis） | **协议型**（Codex / Claude Code） |
|---|---|---|
| 插件是什么 | JS 代码，加载进对方的 DI 容器 | skill(Markdown) + MCP 配置 + hook(可执行文件) + subagent(声明文件) 的**打包** |
| 兼容代价 | 必须引入对方的运行时与接口包 | **实现同样的目录约定与线上协议即可** |
| 语言 | 锁死 TS/JS | 任意 |
| 谁是宿主 | 对方的容器 | **你自己** |

OpenAI 对 plugin 的官方定义原文：
> "Plugins are **distribution wrappers** bundling skills + MCP server configs +
> app mappings + presentation assets."

**插件是打包器，不是代码。** 这就是它能语言无关、能被任意应用嵌入的原因。

**② 我们已经长在协议型这一边了，只差临门几脚**（核实见 §1.3）

所以正确的解法不是去适配谁，而是：**把我们本来就在走的路走完，让契约成为我们自己的**，
别人的生态是插进来的，不是我们插进别人。

`skills.py:136 _load_frontmatter_skill` 已是 `SKILL.md` + YAML frontmatter；

**审批 —— 三值语义一一对应**

`permission.py:14` 是 `APPROVE / DENY / ABORT`；
Codex 的反向审批请求响应是 `accept / decline / cancel`。**同构，直接映射。**

**stream 输出 —— 已经对齐过一次别人的协议**

`stream_json.py` 的模块 docstring 原文：
> "事件字段名对齐 Claude Code 的 stream-json 输出（system/init → assistant →
> user/tool_result → result），让 IvyeaOps 等已解析 Claude Code 格式的消费方可以
> 复用同一套渲染。**唯一有意差异：计价单位是人民币，用 `total_cost_cny` 而不伪装成
> `total_cost_usd`。**"

**这是本方案全部"对齐"论证的先例**：用别人的字段名 → 别人的消费方零改动可用 →
但主权字段坚持自己的。已经验证过，IvyeaOps 的 runner 因此省掉一整套解析。

### 1.4 开源自托管的硬约束

这条约束贯穿全案，是很多取舍的**唯一裁决依据**：

| 约束 | 来源 | 对本案的影响 |
|---|---|---|
| 纯 Python 3.9+，pip 可装 | `pyproject.toml` | 内核不得引入 Node/Rust 运行时 |
| 刻意不用 torch | `pyproject.toml` 注释：pip 会给 Linux 拉 GB 级 CUDA 版，小内存机直接 OOM | 任何重依赖必须是可选插件 |
| Windows 必须能跑 | 既有纪律：`encoding="utf-8"`、`no_window_kwargs`、`os.pathsep` | 新增路径/进程调用同此 |
| 用户自己的机器 | 自托管定义 | 不得要求外部账号、不得联网才能启动 |
| lockfile 必须公共 registry | 既有事故：本机 npm 镜像把 `resolved` 写死成内网地址，用户机崩 | 任何 npm 相关产物同此 |

**推论**：Cordis 兼容层要 Node + npm + 一组 `@deepseek-ai/*` 包，
参照本机 dsh-web 的实际开销（systemd 限到 `MemoryHigh=600M / MemoryMax=900M`，
且"必走 npm 包别源码构建，2vCPU 会 OOM"）——
**开源自托管产品不能要求用户为了插件生态先装个 Node 环境。**
这不是保守，是这条约束的硬性结论。

## 2. 目标与边界

### 2.1 目标

| # | 目标 |
|---|---|
| G1 | **契约归我们**：内核只持有插件契约，不持有任何具体能力 |
| G2 | **语言无关**：第三方不写 Python 也能做插件 |
| G3 | **双向生态**：既能用别人的 skill，我们的 skill 也能被别人用 |
| G4 | **智能路由**：按任务自行决定调哪些 skill / 插件，且**不因数量增长而劣化** |
| G5 | **市场统一**：门道 = 上游 registry，ops = 消费端，同时容纳 skill 与 plugin |
| G6 | **零回归**：现有功能一个不坏，生产两个 systemd 服务不停机 |
| G7 | **自托管友好**：内核装机成本不因插件化上升一分 |

### 2.2 非目标

| 不做 | 理由 |
|---|---|
| 在内核里复刻 Cordis | 那是代码型生态的入场券，不是我们的契约。要它时以可选插件形式引入（§7.3） |
| 追求跑通 dsh 的前端 UI 插件 | 需要对方的 client runtime + SlotRegistry + React。可选层可覆盖一部分，不做承诺（§7.3） |
| 把 IvyeaOps 合进 agent 进程 | 见 §9.1，回归面失控 |
| 复刻 Codex 的 Rust 实现 | 我们对齐的是**协议**，不是实现 |

### 2.3 一条贯穿始终的纪律

> **对齐字段名和方法名，不对齐价值观。**

`stream_json.py` 已经立好了范例：对齐 Claude Code 的事件名，
但计价坚持 `total_cost_cny` 不伪装成 `total_cost_usd`。
本案所有对齐都遵此——**主权保留清单见 §5.4**。

### 2.4 先补的地基：LICENSE

核实发现 `ivyea-agent` 仓库**没有 LICENSE 文件**，`pyproject.toml` 也无 license 字段
（`ivyea-ops` 有）。没有许可证 = 法律上保留所有权利 = 别人不能合法使用、fork、写插件。

**对一个要建插件生态的开源自托管项目，这是地基级缺口。**
建议 MIT（与 ops 一致），且 `pyproject.toml` 补 `license` 字段。
**这一条不依赖本方案任何决策，随时可以先做。**

## 3. 设计原则

### 3.1 内核只持有契约——但"内核"要有个可证伪的定义

照抄 dsh 做对了的一条：**没有特权 core**。它的 `dsh-base` 是一个 *bundle*，
往空的插件树里 insert 行，而不是一个内核。

但"一切皆插件"如果不给判据，就会变成口号。**判据如下**：

> **一个模块是内核原语，当且仅当：没有它，agent 跑不完一个轮次。**
> 其余一律是插件。

按这条判据实测归类（`agent_loop.py` 的直接依赖 + 各模块行数）：

| 模块 | 行数 | 归类 | 理由 |
|---|---|---|---|
| `agent_loop` / `context` / `sessions` | — | **内核原语** | 轮次本身 |
| `routing`（三车道判定） | 188 | **内核原语** | 决定这一轮怎么跑 |
| `task_scope` / `progress_reporting` | 432 / — | **内核原语** | 轮次内的纪律 |
| `stream_json` | — | **内核原语** | 轮次的对外表达 |
| `permission` | — | **内核原语** | 审批是轮次的一部分 |
| **`agent_tools`（54 个工具）** | — | **插件** | 没有工具，轮次照样能跑（只是干不了活） |
| **`knowledge`** | **2400** | **插件（但 P0 不动）** | ⚠️ 见下 |
| **`vision`** | 605 | **插件（但 P0 不动）** | 同上 |
| **`memory` / `memory_core` / `retrieval`** | — | **插件（但 P0 不动）** | 同上 |

#### ⚠️ 诚实说明：knowledge / vision / memory 在 P0 不会变成插件

`agent_loop.py:9` 的 import 行实测：

```python
from . import (config, context, knowledge, panels, progress_reporting,
               stream_json, task_scope, ...)
```

**`knowledge`（2400 行）是被 agent_loop 直接 import 的**，`vision.route_images`
也在轮次里被调用。按上面的判据它们该是插件，但把它们抽出来是一次**独立的大重构**，
和插件契约本身无关。

**处理方式**：
- P0 **不抽**。它们留在内核里，但在 ADR-0016 里**明确记为"待抽取的内核债"**
- 插件契约设计时**预留它们的 seam**（`knowledge` / `vision` / `memory` 各是一个扩展面的候选），
  这样将来抽取时契约不用改
- **不在文档里假装它们已经是插件**——v2 初稿的 §3.1 图里画了个 `ivyea-knowledge`，
  正文却从没设计过它，这是自欺

所以本方案兑现的"一切皆插件"，准确表述是：

> **能力面（工具 / 技能 / UI / 钩子 / 子代理）一律是插件；
> 轮次机制（循环 / 上下文 / 会话 / 路由 / 审批 / 流式）是内核原语；
> 知识 / 视觉 / 记忆是已识别的待抽取内核债，契约为它们预留位置。**

这个表述可证伪，而"一切皆插件"不可证伪。

#### 结构

```
IvyeaAgent 内核 = PluginHost + 五个扩展面契约 + 轮次原语
                  └── 外加三笔已登记的待抽取内核债（knowledge / vision / memory）

自带件（默认随包，都是插件，都能卸）
  └── ivyea-core-tools   54 个现有工具
  └── ivyea-web          自带前端

用户装的
  └── ivyea-ops │ 第三方协议型插件 │ [可选] ivyea-cordis-host
```

**P0 的可证伪验收**：卸载 `ivyea-core-tools` 后 agent 仍能启动并跑完一个无工具轮次。

### 3.2 Cordis 论文的三个贡献，逐条裁决

| 论文贡献 | 解决什么 | 我们 |
|---|---|---|
| **① Revertible effects**（每个 context 变换携带逆操作） | 卸载能干净回滚，不留幽灵监听器 | ✅ **全借**。这是插件化的地基——没有它"卸载插件"只是口号。落成 `register_*() → disposer`，逆序执行，由 `ivyea plugin test` 自动验证 |
| **② Reactive coeffects**（依赖变化自动重挂） | 支撑 HMR | ⚠️ **只借声明不借反应**。取 `requires` 做启动期拓扑排序，不做运行时自动重挂——我们 `systemctl restart` 是秒级 |
| **③ 统一 effect/coeffect context** | 形式化的系统级可组合性保证 | ❌ **不借**。插件数量两位数、依赖是浅层的，显式拓扑排序 + 启动期报错就够 |

一句话：**论文最值钱的是①，最难抄的是③，而③恰好是我们最不需要的。**

### 3.3 协议型优先，进程内是例外

| 形态 | 谁用 | 隔离 | 语言 |
|---|---|---|---|
| **协议型**（skill / MCP / hook / subagent） | **第三方默认** | 进程级或纯文件 | 任意 |
| **进程内 Python**（`entry_points`） | 仅第一方自带件 | 无 | 仅 Python |

进程内形态有**硬约束**：只许用 stdlib + agent 已有依赖，不许在 `setup()` 里做网络 IO，
不许 import 重依赖。理由是 §1.4——一个进程内插件带错 numpy 版本就能把 onnxruntime 干掉。

**市场对进程内插件的第三方投稿默认拒绝**（§8.3）。

## 4. 核心设计：五个扩展面

契约就是这五个面。**一个插件 = 在这五个面上做贡献的一个打包。**

| 扩展面 | 形态 | 语言无关 | 现状 |
|---|---|---|---|
| **① Skill** | `SKILL.md` + YAML frontmatter + `scripts/` `references/` `assets/` | ✅ 纯文件 | 已有，差一个目录 |
| **② Tool** | MCP server（stdio / streamable-http）或 HTTP 能力目录 | ✅ 协议 | 已有 `mcp_client.py` + ops bridge |
| **③ Hook** | 7 个生命周期事件，条目是可执行文件 | ✅ 子进程 | 已有 6/7 |
| **④ Subagent** | 声明式配置文件（name/instructions/model/tools/sandbox） | ✅ 纯文件 | 有工具形态，无声明形态 |
| **⑤ UI** | 面板贡献声明 + 静态资源 | ✅ 声明+资源 | 无 |

### 4.1 ① Skill

沿用现有实现，改三处：

1. **扫描根加 `~/.agents/skills`**（§7.1 的战略理由）。优先级：
   ```
   内置(bundled) < 插件贡献 < ~/.agents/skills < ~/.ivyea/skills(个人) < 项目 .agents/skills
   ```
   保留既有纪律：**外部库不覆盖内置**（`skills.py:list_skills` 的注释记着这个坑）。
2. **渐进披露**：会话起始只注入元数据（name/description/whenToUse），选中才读全文。
   Codex 的做法是元数据 ~8KB 上限——我们照做，且这直接服务于 §4.6 的 token 预算。
3. **frontmatter 新增两个可选字段**（服务于 §4.6 的 L3 路由）：
   ```yaml
   plugins: [ivyea-ops]                       # 该 skill 需要哪些插件
   tools:   [ops__listing_scrape, ops__asin_audit_start]   # 更精确：需要哪些工具
   ```

### 4.2 ② Tool

**工具一律经协议进来，内核不认 Python 函数指针。**

两种来源：

| 来源 | 契约 |
|---|---|
| **MCP server** | 标准 MCP。工具名空间化为 `<ns>__<name>` |
| **HTTP 能力目录** | `POST {catalog_path}` → 工具清单；`POST {invoke_path} {name, arguments}` → 结果。IvyeaOps 现有的 `/bridge/tools` + `/call` **就是这个契约**，不用改 |

**命名契约（第二轮复核澄清）**：

现有代码里 MCP 集成用的**不是**逐个命名，而是门面：
`mcp_list_tools` / `mcp_call_tool(server, tool)`（`tools_general.py:1061,1130`）。
这与 ops bridge 的 `ivyea_ops_list_tools` / `ivyea_ops_call_tool` 是**同一个模式**。

→ **L1 门面折叠是既有事实，而且已有两个生产先例**，不是新发明。因此命名规则是：

| 暴露层级 | 模型看到的名字 |
|---|---|
| **L1 门面（默认）** | 只有 `<ns>_list_tools` / `<ns>_call_tool` 两个。**单个工具不进 schema，也就没有名字** |
| **L2/L3 提升后** | 才生成 `<ns>__<name>`（双下划线分隔，与既有单下划线工具名不会歧义） |

**别在 L1 阶段就给每个工具起名**——那正是要避免的 token 开销。

工具元数据（两种来源统一）：

```jsonc
{
  "name": "listing_scrape",
  "title": "采集 Listing 数据",              // 中文标题，进语义路由的向量
  "description": "...",
  "parameters": { /* JSON Schema */ },
  "readonly": false,
  "destructive": true,        // 是否需要审批
  "long_running": true,       // 是否给宽限超时
  "parallel_safe": false      // 能否与兄弟调用并行
}
```

> IvyeaOps 的 `_public_tool()` 已经返回了其中 6 个字段，只需补 `readonly` 和
> `parallel_safe`。**契约不是新发明的，是把生产里已经跑着的东西写成规格。**

**内置 54 个工具怎么办**：打包成 `ivyea-core-tools` 插件，走进程内形态注册。
`TOOL_SCHEMAS` / `PARALLEL_SAFE` / `READONLY_TOOLS` / `dispatch` / `dispatch_result`
五个符号名**必须保留且语义不变**——已核实 9 处调用方
（`agent_loop.py:18,326,466,522`、`cli.py:1502,1762,2051`、`context.py:185`、`service.py:2606`）。

### 4.3 ③ Hook

现有 6 个事件 + **补 `permission_request`** = 7 个，与 Codex 对齐：

| 事件 | 可阻断 | matcher | 现状 |
|---|---|---|---|
| `session_start` | ✅ | source(start/resume/clear) | 有 |
| `user_prompt` | ✅ | — | 有 |
| `pre_tool_use` | ✅ | tool_name 正则 | 有 |
| **`permission_request`** | ✅ allow/deny/abstain | tool_name 正则 | ❌ **新增** |
| `post_tool_use` | ❌ | tool_name 正则 | 有 |
| `stop` | ❌ | — | 有 |
| `session_end` | ❌ | — | 有（我们多的，保留） |

`permission_request` 的价值：**让审批策略可外挂**。
企业用户可以写一个 hook 脚本对接自己的工单系统，而不必改我们的代码。
`abstain`（弃权）是关键的第三态——hook 不表态时落回内置的审批三档（ADR-0011）。

### 4.4 ④ Subagent

现在 subagent 是一个工具（`dispatch_subagent`），改成**声明式 + 工具**双轨：

```toml
# ~/.ivyea/agents/ads-analyst.toml  或  项目内 .agents/agents/ads-analyst.toml
name = "ads-analyst"
description = "广告数据分析专员，只读"
instructions = "..."
model = "deepseek-chat"          # 可选，缺省继承主脑
tools = ["run_patrol", "run_account_diagnosis", "knowledge_search"]
readonly = true
```

好处：**用户不写代码就能定制专家 agent**，且这些声明可以进市场分发。
`dispatch_subagent` 工具保留，多一个 `agent` 参数指定用哪份声明。

### 4.5 ⑤ UI

**这是 v1 最大的缺失——UI 契约必须和其他四面同期定死，否则后面所有 UI 插件都要返工。**

```jsonc
"ui": {
  "panels": [{
    "id": "ops-dashboard",
    "title": "运营驾驶舱",
    "icon": "📊",
    "slot": "sidebar",              // sidebar | main | overlay | settings
    "entry": "./ui/panel.js",       // 或 "iframe": "https://..." 
    "priority": 100
  }]
}
```

槽位语义（借 dsh 的 SlotRegistry，但只取最小集）：

| 槽位 | 语义 |
|---|---|
| `sidebar` | 列表叠加（additive） |
| `main` | 单槽，遮蔽（priority 高者赢） |
| `overlay` | 列表叠加，默认 pointer-events: none |
| `settings` | 列表叠加，设置页分区 |

两种 entry：
- **`entry`**：ESM 模块，导出 `mount(el, ctx)` / `unmount(el)`。零框架要求
- **`iframe`**：直接嵌一个 URL。**IvyeaOps 的板块就走这条**——零改造

> **刻意不要求 React**。自带 web 用原生 ESM（§6.2）。
> 要求第三方装一整套前端工具链才能贡献一个面板，是把生态门槛抬到没人来。

### 4.6 工具数量爆炸——本方案最大的技术风险

**不是理论担忧，`routing.py` 的 docstring 里记着线上实测：**

> "慢的从来不是模型（DeepSeek 官方实测单次 1.3–2.5s，挂上全部 **54 个工具也只多 0.5s**），
> 慢的是**步数**。"
> "一句「测试」跑了 **18 步**，其中 17 步是 `progress_update`/`todo_write`，
> 工具自身耗时 0.0s，用户等了 **2 分 16 秒**。"
> "最近 300 次工具调用里 **112 次（37%）** 是这类纯记账调用。"

硬数字：**54 个工具 ≈ 6.9K token**。
54(内置) + 44(ops) = 98，再加第三方 → 线性外推 **12.5K+ token/轮**，
而真正的代价是上面那条规律：**工具越多，模型越倾向"顺手多调一个"，步数越滚越长。**

#### 三级渐进暴露

**L1 门面折叠（默认，零成本）**

每个插件默认只暴露 2 个工具：
```
<ns>_list_tools(query?)          → 该插件的工具目录
<ns>_call_tool(name, arguments)  → 调用
```
100 个第三方工具 → prompt 里只占 2 个 schema。
**这套东西现在就在生产跑**（`ivyea_ops_list_tools` / `ivyea_ops_call_tool`，
`agent_tools.py:693,722`），只是从 ops 专用泛化成插件通用。

**L2 语义提升（新建）**

> **核实修正**：v1 写"复用 `routing.py`"是**错的**。`routing.py` 是关键词三车道分类器
> （`chat`/`board`/`work`），docstring 明写 board 车道"工具集**不裁**（裁了就可能缺能力）"。
> 它解决"该几步就几步"，不是"该挂哪些工具"。

建在已有的语义检索设施上（这些是实际存在的）：
`onnx_embedding.encode_many()` / `retrieval_embeddings.encode_query()` / `.cosine()`。

**延迟实测（第二轮复核，全新进程实跑）**：

```
import onnx_embedding          0.00s   （懒加载）
首次 encode（含模型加载）      0.20s   （一次性）
热态单次 encode                2.6ms
批量编码 98 个工具             0.20s   （装载时做一次，落盘缓存）
模型 bge-small-zh-int8，512 维
```

→ **L2 的每轮开销约 3ms，可忽略。** 这个数字先量出来，
免得实施时有人担心"每轮加一次向量编码会不会拖慢"而擅自砍掉这一层。

1. 插件装载时预编码每个工具的 `title + description`，落盘缓存（随插件版本失效）
2. 每轮编码用户原话（用 `task_scope._user_said` 切掉系统注入块——
   `routing.py` 的 docstring 明确记着：拿注入块判意图正是上一次事故的成因）
3. 余弦 top-K（默认 8）提升为一等工具
4. 未命中的插件仍走 L1

**与 `routing.py` 串联不是替代**：先由 routing 判车道（`chat` 车道直接不挂任何工具），
再由 L2 在 `board`/`work` 车道内决定挂哪些。

**L3 skill 引路（最精确）**

skill 的 frontmatter 声明 `plugins` / `tools`（§4.1），命中该 skill 时自动提升其声明的工具。

> **这直接回答了"agent 会根据任务自行决定调不调用 skill 和插件"**：
> skill 的路由本来就是语义匹配，skill 再把插件带进来，形成两级路由。

### 4.7 权限与审批

**现状问题**：破坏性操作的审批逻辑写死在 `_t_ivyea_ops_call_tool` 里
（`agent_tools.py:722-745`），只保护 ops 工具。必须上提到统一收口。

```
dispatch_result(name, args, ctx)
  ├─ 1. 查注册表拿 entry（readonly / destructive / plugin_id）
  ├─ 2. plan_mode 检查              → 破坏性工具直接拒
  ├─ 3. 插件授权检查                → 该插件是否被授予 destructive 权限
  ├─ 4. hook: pre_tool_use          → 可否决（已有）
  ├─ 5. hook: permission_request     → allow / deny / abstain（新增）
  ├─ 6. 内置审批三档                 → abstain 时落到这里（ADR-0011）
  ├─ 7. around_tool_use              → 超时/重试/计量包裹（新增）
  ├─ 8. 执行
  └─ 9. hook: post_tool_use          （已有）
```

与审批三档的对齐：
- **只读**档：插件的 destructive 工具**不挂 schema**（不是挂了再拒——省 token 且模型不会反复试）
- **审批放行**档：挂 schema，执行前弹审批卡
- **完全放行**档：直接执行

第三方插件额外一层：`permissions.default_grant: "readonly"`，
首装只给只读，破坏性能力要显式再放行。

### 4.7b 安全模型：第三方插件的凭据隔离（复核新增）

> **复核发现的严重缺口**：现有子进程调用**全部继承完整环境变量**，没有任何清洗。
> 单机自用时无害；一旦插件来自市场，这是**凭据外泄的直通道**。

实测两处：

```python
# mcp_client.py:95 —— 没有 env= 参数，子进程继承父进程全部环境
self._proc = subprocess.Popen([self.command, *self.args],
                              stdin=PIPE, stdout=PIPE, stderr=PIPE, ...)

# hooks.py:97 —— 显式复制全量环境
def _hook_env(event, payload):
    env = dict(os.environ)          # ← DEEPSEEK_API_KEY / 领星凭据 / 全部在内
    env["IVYEA_HOOK_EVENT"] = event
    ...
```

对照：dsh 的 `dsh-mcp-client` 的配置字段注释明写
"Extra env vars merged on top of **scrubbed** ambient env"——**它清洗，我们不清洗。**

#### 三层隔离规则

| 插件来源 | 环境变量策略 |
|---|---|
| **自带件**（`plugins_builtin/`） | 继承全量（与今天行为一致，零回归） |
| **用户手动装的**（`~/.ivyea/plugins/`） | 默认白名单，装载时提示可放宽 |
| **市场装的** | **强制白名单**，不可放宽 |

白名单默认只含：`PATH`、`HOME`/`USERPROFILE`、`LANG`/`LC_*`、`TZ`、
`TEMP`/`TMP`、`SYSTEMROOT`（Windows 必需）、以及 manifest 里
`permissions.env` **显式声明**的键。

```jsonc
"permissions": {
  "env": ["MY_PLUGIN_TOKEN"],        // 只有声明了才透传，且安装时向用户展示
  "network": ["https://api.example.com"],
  "filesystem": "workspace"
}
```

#### 落点

- `mcp_client.MCPClient.__init__` 增加 `env_policy` 参数，`Popen` 补 `env=`
- `hooks._hook_env` 增加来源参数，按上表决定是否清洗
- **两处都必须保留"自带件继承全量"的分支**，否则动了今天的行为

#### 顺带：hook 的可移植性

`hooks.py:103 _shell()` 已经处理了平台差异
（`["cmd","/c",cmd]` vs `["bash","-c",cmd]`）✅。
但**插件带的 hook 命令本身**可能是 `./hooks/guard.sh`——Windows 上跑不了。

→ manifest 的 hook 条目支持按平台分列，`lint` 阶段校验：
```jsonc
"hooks": [{ "event": "pre_tool_use", "matcher": "lingxing_.*",
            "command": "./hooks/guard.sh",
            "command_windows": "./hooks/guard.ps1",   // 缺省时 lint 报警
            "timeout": 30 }]
```

### 4.7c 插件生命周期与启动成本（复核新增）

> **复核发现的设计缺口**：v2 没有回答"装了 20 个 MCP 插件，`ivyea chat` 启动要多久"。

实测现状：`mcp_client._ensure_stdio()` 是**懒启动**（首次 RPC 才 spawn）✅。
但要知道一个插件**有哪些工具**，必须调 `list_tools()`——那就会 spawn。
20 个插件 = 启动时 20 个子进程，CLI 冷启动直接毁掉。

#### 解法：工具目录磁盘缓存 + 真正的懒连接

```
~/.ivyea/plugins/<id>/.catalog.json     # 装载时写一次
{
  "plugin_version": "1.2.0",
  "captured_at": "2026-08-22T...",
  "tools": [ {name, title, description, parameters, readonly, destructive, ...} ]
}
```

- **`ivyea plugin install` / `update` 时**：spawn 一次，抓目录，落盘，杀掉子进程
- **正常启动时**：只读 `.catalog.json`，**一个子进程都不起**
- **首次真正调用某插件的工具时**：才 spawn，之后进程复用
- **缓存失效**：`plugin_version` 变化，或用户显式 `ivyea plugin refresh <id>`
- **目录漂移兜底**：调用时若返回 `UNKNOWN_TOOL`，自动 refresh 一次再重试，并记 warning

**这个缓存同时是 §4.6 L2 语义提升的输入**——工具向量在装载时就能预编码，
不必等运行时。两件事复用同一份产物。

### 4.7d 多客户端并发下的审批归属（复核新增）

> **复核发现**：门面层（§5）让多个客户端能同时连一个 IvyeaAgent
> （VS Code + 自带 web + CLI）。此时"审批卡弹给谁"没有定义。

现状是好的基础：`service.py:46` 的 `_PENDING_APPROVALS` 按 `request_id` 键，
单槽队列，三条兜底路径（超时 / 客户端断开 / 进程重启）**全部收敛到拒绝**，
绝不把 agent 永久挂在没人回的确认上。**这个设计直接沿用，不重新发明。**

需要补的是**归属**：

| 规则 | 说明 |
|---|---|
| 审批请求带 `thread_id` + `origin_client_id` | 从发起该轮次的客户端继承 |
| **谁发起的轮次，审批就回给谁** | 对齐 Codex 的 "approvals bubble up to active UI **labeled by source thread**" |
| 其他客户端**可见但不可决** | 只读展示，避免两个客户端抢答 |
| 发起客户端断开 | 落到既有的"断开即拒绝"兜底，不改 |

`GET /v1/chat/permissions/pending` 加一个 `client_id` 过滤参数；
不传时保持今天的全量返回（**向后兼容，ops 现有消费方不受影响**）。

### 4.7e 三个实施期会咬人的细节（第二轮复核）

#### ① Windows：每个 MCP 插件 spawn 都会弹黑框

`mcp_client.py:95` 的 `Popen` **没有 `creationflags`**：

```python
self._proc = subprocess.Popen([self.command, *self.args],
                              stdin=PIPE, stdout=PIPE, stderr=PIPE, ...)
                              # ← 缺 creationflags
```

单机配一两个 MCP 服务器时没人注意；**插件普及后就是 N 个黑框闪。**

对照：IvyeaOps 已经有现成的 `app.core.proc.no_window_kwargs()`
（`brain_chat_service.py:323` 在用），agent 侧只有 `self_manage.py:259` 的
`DETACHED_PROCESS`（那是守护化用的，不是这个）。

→ **agent 侧补一个同名 helper**，`mcp_client` 与将来所有插件 spawn 统一走它。
与 §4.7b 的 `env=` 是同一处改动，一起做。

#### ② stdio 门面会和 CLI 抢 stdin/stdout

`ivyea chat` 用 stdin/stdout 做交互；stdio 上的 JSON-RPC 也用 stdin/stdout。
**两者不能共存于同一个默认入口。**

→ 门面的 stdio 传输必须是**独立子命令**：`ivyea app-server`（或 `--stdio` 显式开）。
`ivyea chat` 的行为一个字不改。HTTP 传输（`/rpc`）不受影响。
这条要写进 §5.2 的实现约束，否则实施时会有人想"给 chat 加个 --json-rpc 开关"。

#### ③ `thread/rollback` 不只是截断 messages

§5.2 说"单文件模型下 rollback 反而更简单（截断 messages 数组重写）"——**过于乐观**。

会话文件是 `{id, created, updated, model, messages, usage}`（`sessions.py:3`），
其中 `usage` 是逐轮累加的（`sessions.py:144 _merge_stats`）。
截掉最后 N 轮的 messages，`usage` 就对不上了。

→ rollback 必须：截断 messages **+ 重算 usage**。
两条路选一：
- **回放重算**：从 0 累加保留下来的轮次（准确，但要求每轮的 usage 单独留痕）
- **逐轮存量**：改成每轮存一份增量，rollback 时减掉（改存储格式，代价大）

建议前者，且**先确认现有 messages 里是否留了每轮 usage**——
如果没留，rollback 只能把 usage 标记为"已失真"而不是给个错的数。
**这一条在 P3 动手前必须先查清楚。**

#### ④ skill 补 frontmatter 会产生"双身份"

内置 skill 的 id 是**点分**的 `amazon.launch_playbook`，
而 Codex / dsh 的 skill name 是 **kebab-case**（dsh 有 `isSkillName()` 强校验）。

而这些点分 id **在别处被引用着**（实测）：
```
evals.py:158            sk.id == "amazon.listing_conversion_audit"
tests/test_skills.py    4 处断言（:13 :28 :29 :113）
```

→ 规则定死：
- frontmatter 的 `name:` 是**对外身份**（kebab-case，给三家生态看）
- `x-ivyea.id` 保留**内部身份**（点分，一个字不改）
- **内部引用一律不动**，`evals.py` 和测试不用改
- 加一条测试钉住两者的映射关系（`amazon.launch_playbook` ↔ `amazon-launch-playbook`），
  防止将来有人只改一边

**两条硬纪律**：
1. **凭据只存引用不存值**（`*_setting` 指向 settings key）。manifest 会进市场、进 git，

2. **`id` 即工具命名空间**，撞名在注册期**拒绝**，不静默覆盖——

### 4.8b 插件配置分层（复核补齐：v2 只提了"三层合并"没定义）

```
① 插件 manifest 里的 defaults          （作者给的）
② ~/.ivyea/settings.json 的 plugins.<id> （用户改的）
③ 环境变量 IVYEA_PLUGIN_<ID>_<KEY>       （部署时覆盖，最高优先级）
```

规则：
- **逐键覆盖，不整块替换**（与 dsh 的 patch 语义**故意不同**——
  dsh 的 patch 是"替换整个 config"，那对声明式插件树合适，对用户配置反直觉）
- `*_setting` 类字段（凭据引用）只能出现在 ②③，**manifest 里写了直接 lint 报错**
- `ivyea plugin info <id>` 输出**三层各自的值和最终生效值**，便于排障
  （凭据值一律脱敏成 `***`，只显示"来自第几层"）

### 4.8c 版本、升级与迁移（复核补齐：v2 完全没写）

#### 契约版本

manifest 的 `schema` 是**契约版本**，内核维护兼容窗口：

| 内核行为 | 条件 |
|---|---|
| 正常加载 | `schema` 在支持列表内 |
| 加载但警告 | `schema` 低于当前但仍在窗口内 |
| **拒绝加载并说明** | `schema` 高于内核所知 → 提示"请升级 IvyeaAgent" |

**破坏性契约变更一律走 ADR**，且必须给一个版本的过渡窗口（新旧同时支持）。

#### 插件升级

- `ivyea plugin update <id>`：装新版 → 跑 `plugin test` → 通过才切换 →
  **失败自动回滚到旧版**并保留旧版目录
- 目录布局 `~/.ivyea/plugins/<id>/<version>/` + 一个 `current` 符号链接
  （Windows 上用一个 `current.txt` 记版本号——**符号链接在 Windows 上要管理员权限**，
  这是既有 Windows 纪律的延伸）
- 升级后工具目录缓存（§4.7c）自动失效重建

#### 老用户迁移（P0 的隐形需求）

现有用户已经在用 `~/.ivyea/skills`、`~/.ivyea/hooks.json`、`mcp.json`。
**P0 不得让他们的现有配置失效。**

| 现有资产 | P0 后 |
|---|---|
| `~/.ivyea/skills/` | **继续原样工作**，只是多了 `~/.agents/skills` 作为另一个来源 |
| `~/.ivyea/hooks.json` | **继续原样工作**，插件贡献的 hook 与之**合并**（不是替换） |
| `mcp.json` 里的 MCP server | **继续原样工作**；`ivyea plugin list` 里以 `legacy-mcp:<name>` 形式展示，提供 `ivyea plugin adopt <name>` 一键转成正式插件（可选，不强制） |
| `skills_builtin/*/skill.json` | 保留一个版本，由 frontmatter 生成，测试钉住一致性（§7.2） |

**验收：一台已在用的老机器升级后，零配置改动、行为不变。**

### 4.9 内核：PluginHost

```
ivyea_agent/plugins/
├── manifest.py      # schema 解析与校验
├── host.py          # 发现 / 装载 / 卸载 / 拓扑排序
├── registry.py      # PluginContext：可逆注册
├── seams.py         # 五个扩展面的接口
├── source_mcp.py    # 复用现有 mcp_client.MCPClient
├── source_http.py   # 上提现有 _ops_bridge_request
└── source_inproc.py # entry_points，仅第一方
```

```python
class PluginContext:
    """交给插件的注册面。每个 register_* 返回 disposer。"""
    plugin_id: str
    settings: Mapping[str, Any]      # 三层合并后的配置
    logger: Logger

    def register_tool(self, meta: ToolMeta, handler) -> Disposer: ...
    def register_skill_root(self, path: Path) -> Disposer: ...
    def register_hook(self, event: str, entry: dict) -> Disposer: ...
    def register_subagent_root(self, path: Path) -> Disposer: ...
    def register_ui_panel(self, spec: dict) -> Disposer: ...

class PluginHost:
    def discover(self) -> list[Manifest]:
        """1. 自带件 ivyea_agent/plugins_builtin/
           2. 用户   ~/.ivyea/plugins/
           3. 环境   IVYEA_PLUGIN_ROOTS（os.pathsep，与 IVYEA_SKILL_ROOTS 一致）
           4. entry_points 组 'ivyea_agent.plugins'"""
    def load_all(self) -> LoadReport: ...
    def load(self, pid: str) -> None: ...
    def unload(self, pid: str) -> None: ...   # 逆序执行全部 disposer
    def reload(self, pid: str) -> None: ...
    def report(self) -> dict: ...             # /v1/plugins 的数据源
```

**失败隔离**：单个插件炸了，内核降级继续跑，`report.failed` 写明原因，
`/v1/plugins` 和 web 上能看到红点。**绝不因第三方插件让主流程起不来。**

## 5. 门面层：协议对齐

### 5.1 先把两个词定义清楚

| 词 | 含义 | 不是什么 |
|---|---|---|
| **对齐** | 我们自己实现同样的**字段名 / 方法名 / 目录约定**，让别人写好的客户端不改代码就能驱动我们 | **不是**引入对方的代码、依赖、账号或运行时 |
| **门面** | 现有内部实现**一行不改**，旁边加一个入口做协议翻译 | **不是**重写内部逻辑 |

**先例就在本仓库**：`stream_json.py` 全文就是一堆构造 dict 的函数，
把内部事件翻译成 Claude Code 的 stream-json 字段名。
`agent_loop` / 工具派发 / 权限一行没动，而 IvyeaOps 的 runner 因此省掉一整套解析。

**对齐的装机成本是 0**：不装任何东西，不联网，不需要任何外部账号。

### 5.2 对齐目标一：Codex app-server（JSON-RPC 2.0）

Codex 在 2026-08-20 以 Apache-2.0 开源了 harness（`codex exec` + SDK + `app-server`）。
`app-server` 是 stdio / WebSocket 上的 JSON-RPC 2.0，已经有一批现成客户端在用：
VS Code 扩展、JetBrains 插件、官方 Python SDK、第三方 Python/Elixir SDK、
Claude Code 的 companion。

**对齐它 = 这些客户端改个地址就能驱动自托管的 IvyeaAgent。**

映射表（左边全部已存在）：

| 我们现有 | 对齐后新增的门面方法 | 缺口 |
|---|---|---|
| `POST /v1/chat/sessions` | `thread/start` | 无 |
| `GET /v1/chat/sessions/{id}` | `thread/resume` | 无 |
| `GET /v1/chat/sessions` | `thread/list` | 无 |
| `POST /v1/chat/stream`（SSE） | `turn/start`（JSON-RPC 通知流） | 无，事件改名 |
| `GET /v1/chat/permissions/pending` + `POST /v1/chat/permission` | 反向请求 `execCommandApproval` / `applyPatchApproval` | **无**——`APPROVE/DENY/ABORT` ↔ `accept/decline/cancel` 三值同构 |
| `/v1/model`、`/v1/model/configure` | `config/read` | 无 |
| `/v1/auth` | `account/read` | 无 |
| — | `turn/interrupt` | ❌ 补 |
| — | `turn/steer` | ❌ 补 |
| — | `thread/fork` | ❌ 补 |
| — | `thread/rollback` | ❌ 补 |
| — | `thread/archive`、`thread/name/set` | ❌ 补 |

**真实缺口 = 6 个方法 + 一层协议翻译。** 其余全是改名。

**一处需要设计决策的差异**：
Codex 的 `thread/resume` 依赖 **rollout JSONL**（逐事件追加），
我们是 `~/.ivyea/sessions/<id>.json` **单文件 JSON**（`sessions.py:65`）。

→ 建议**保留单文件 JSON 作为权威存储**，门面层按需投影成 JSONL 事件流。
理由：单文件 JSON 是原子写（`sessions.py:120` 的 tmp+rename 已处理并发），
改成追加式 JSONL 要重做并发与截断处理，**为了协议长相去改存储层是本末倒置**。
`thread/rollback` 在单文件模型下反而更简单（截断 messages 数组重写）。

### 5.3 对齐目标二：Claude Code stream-json（已完成）

不需要做任何事——`stream_json.py` 已经对齐。
本方案只做一件事：**把它写进契约文档**，让它成为承诺而不是巧合。

### 5.4 主权保留清单（对齐但不投降）

以下字段/行为**故意不对齐**，且必须在文档里写明原因，防止后人"顺手改齐"：

| 项 | 我们的 | 别人的 | 原因 |
|---|---|---|---|
| 计价单位 | `total_cost_cny` | `total_cost_usd` | 已有决定：不伪装币种（`stream_json.py` docstring） |
| 会话存储 | 单文件 JSON | rollout JSONL | §5.2，存储层不为协议长相让步 |
| `session_end` 事件 | 保留 | Codex 无此事件 | 我们的 hook 使用方在用 |
| 审批三档 | 只读/审批/放行（ADR-0011） | sandbox×approval 组合 | 我们的语义更贴业务，且已有生产使用方 |
| 知识引证 `[K#]` | 保留 | 无对应 | 亚马逊知识库的核心特性 |
| 视觉三档降级链 | 保留并上报 `vision_tier` | 无对应 | 降级本身不是问题，降级了不说才是 |

### 5.5 门面层不碰什么

**ADR-0005 那条链一行不动**：长任务不因客户端断开白跑、断链改轮询落盘、
serve 心跳、`defer_citation_text` 引证流式。

门面只做协议转换，**内部仍走现有 `/v1/chat/stream` 管线**。
重写这条链等于把踩过的坑重踩一遍。（风险登记 R7）

### 6.3 `ivyea-ops`：任务台与板块

**进程边界：ops 保持独立 systemd 服务，不合进 agent 进程。**

| 方案 | 影响面 | 结论 |
|---|---|---|
| ops 合进 agent 进程 | FastAPI / 前端 dist / `auth_request` 登录鉴权 / autofix worktree / 93 个 agents 端点全部重新安置 | ❌ 否决 |
| ops 以插件形式接入（tools 走 http 面，UI 走 iframe 面） | 只改 agent 侧注册方式 + ops 补两个字段一个端点 | ✅ 采纳 |

**ops 侧几乎不用改**：`_public_tool()` 已返回 6 个契约字段，补 `readonly` + `parallel_safe`，
再加一个 `GET /api/ivyea-agent-bridge/manifest` 让 agent 自动发现。

#### 6.3.0 ⚠️ 认证方向反了——P1 的阻塞项（第二轮复核发现）

现有 bridge token **只为一个方向设计**：

```
routers/ivyea_agent.py:263  →  ivyea_ops_tools.issue_bridge_token()
_BRIDGE_MAX_AGE_SECONDS = 15 * 60
```

它是 **ops 在下发嵌入式对话配置时**顺手签的，15 分钟有效。
成立的前提是「**ops 嵌入 agent 的对话**」——ops 是主动方，它知道自己是谁。

但插件模型是**反过来的**：**agent 启动时加载 ops 插件，主动去连 ops。**
此时没有任何人给 agent 签 token，而且 15 分钟的短令牌也撑不起一个常驻插件连接。

**→ 不需要新设计，ops 已经有对的东西**：`server/app/routers/mcp_tokens.py`

```python
class IssueBody(BaseModel):
    name: str = ""              # 令牌用途标注
    scopes: List[str] | None    # 能力范围
    ttl_days: int = 0           # 长期有效
router = APIRouter(dependencies=[Depends(require_admin)])   # 仅管理员可签
```

其模块 docstring 写得正是这件事：
> "发令牌是把这台机器的一部分能力交出去，所以这一整组接口只对管理员开放——
> 即使某个用户被授予了广告或知识库板块，他也不能自己签一个绕过界面的通道。"

**采用方案**：
- ops 插件的认证改用 **`mcp_tokens`**（长期、带 scope、管理员签、可吊销）
- 用户在 ops 的设置页点"生成 IvyeaAgent 接入令牌"→ 粘进 agent 的
  `settings.json` 的 `plugins.ivyea-ops.token`（走 §4.8b 的第②层，凭据不入 manifest）
- **15 分钟的 `issue_bridge_token` 保留不动**——嵌入式对话那条路径继续用它，
  两条路各自认证，零回归
- `scopes` 正好对上 §4.7 的权限模型：只读令牌 / 完全令牌

> **这条不解决，P1 第一步就卡住。** 它排在 P1 的最前面。

#### 6.3.2 任务台：作为 UI 插件接入，而不是搬迁

v1 曾以"93 个端点"为由把这件事降级——**那是拿工作量当借口，已撤回**。

**19 个 HTTP + 2 个 WS 才是任务台。** 其中 agent 已有对等实现 7 个
（health / catalog / auth-status / models / skills / 会话增查 / 审批）。

**净缺口 = 12 个端点 + WS 适配层**——而这 12 个里有 6 个正是 §5.2 要补的
`turn/interrupt`、`turn/steer`、`thread/fork` 等。**两件事是同一件事。**

前端侧实测：`client/src/agents/` 333 个文件 / 44,610 行，
**只有 4 处相对引用逃出子树**（`lib/scrollLock`、`lib/themes` ×2、`lib/termTheme`），
`@/` 别名引用 **0 处**。它本来就是自带 `App.tsx`/`main.jsx`/`i18n`/`stores` 的独立 React 应用。

**结论：任务台不是"搬进内核"，是"注册成一个 UI 插件"。**
两条路径任选：
- **快路**：`ui.panels[].iframe` 指向 ops 的任务台 URL。**零改造**，当天可用
- **深路**：子树复制进 agent 仓库 + 带走 3 个 lib 文件 + 拆掉 Tailwind 三重隔离
  （独立部署后不再需要与 ops 主应用共存——**是减法不是加法**）

建议**先快路后深路**：快路验证 UI 契约设计对不对，深路再谈。

**`/shell` 终端 WS**：搬，但**默认关闭**，`--enable-shell` 显式开启。
agent serve 默认绑 `127.0.0.1`，一旦有人 `--host 0.0.0.0`，默认开启的远程 shell
就是直接的 RCE 面——ops 那边有登录鉴权兜着，agent 没有。
（与 §6.3.1 "不给 `terminal` 补 OpsTool" 是同一条判断。）

## 7. 生态互通

### 7.1 `~/.agents/skills` 是三家的共同约定

| 产品 | skill 根 |
|---|---|
| **Codex** | 系统 → `/etc/codex/skills` → **`$HOME/.agents/skills`** → 仓库 `.agents/skills` |
| **DeepSeek Harness** | `~/.dsh/skills` + `$DSH_AGENTS_HOME`（默认 **`~/.agents`**）；`SkillSource` 枚举含 `user-agents`/`project-agents` |
| **Claude Code** | `AGENTS.md` 约定同源 |
| **IvyeaAgent** | `~/.ivyea/skills` ❌ **没扫 `~/.agents`** |

格式三家一致：`SKILL.md` + YAML frontmatter。

**这不是"我们去兼容谁"，这是一个已经形成的事实标准，而我们碰巧站在外面。**

### 7.2 关键：这是双向的——但输出这一半现在还不成立

| 方向 | 效果 | 现状 |
|---|---|---|
| **输入** | 用户装在 `~/.agents/skills` 的任何 skill，IvyeaAgent 直接可用 | 改一行扫描根即可 |
| **输出** | 我们的 skill 放进 `~/.agents/skills`，Claude Code / Codex / dsh 三家同时能用 | ❌ **当前做不到，见下** |

#### ⚠️ 阻塞项：7 个内置 skill 全部没有 YAML frontmatter

实测（`find skills_builtin -name SKILL.md`，逐个查首行是否为 `---`）：

```
内置 skill 总数 7
带 YAML frontmatter 的 0
```

它们走的是**另一条路**：目录里放 `skill.json`（`skills.py:165 _load_skill` 里
skill.json 优先），`SKILL.md` 本身是纯 Markdown，从 `# Amazon Launch Playbook` 直接开始。

```jsonc
// skills_builtin/amazon/launch_playbook/skill.json
{ "id": "amazon.launch_playbook", "title": "...", "domain": "amazon",
  "version": "2026.06", "description": "...",
  "triggers": ["launch","新品","冷启动","自动广告","测词"],
  "knowledge_ids": ["playbook.launch_maturity_strategy", ...],
  "tools": ["knowledge_search","run_patrol","run_account_diagnosis","recall"] }
```

**Claude Code / Codex / dsh 三家都只读 YAML frontmatter，没有一家读 `skill.json`。**
把当前的内置 skill 放进 `~/.agents/skills`，它们会看到一个没有 name / description 的
SKILL.md —— 要么跳过，要么显示成无名条目。

→ **P0 必须给 7 个内置 skill 补 YAML frontmatter**，否则"输出"只是一句空话。

**怎么补而不制造双份维护**（这是关键，不是补上就完了）：

`skills.py` 的既有语义是 skill.json 优先、frontmatter 兜底。直接两份并存会漂移。
做法：**frontmatter 成为唯一权威**，`skill.json` 里 frontmatter 表达不了的字段
（`knowledge_ids` / `triggers`）**迁进 frontmatter 的自定义键**：

```yaml
---
name: amazon-launch-playbook
description: Guide launch-stage ASIN advertising without prematurely suppressing discovery traffic.
description_zh: 新品期广告打法：别过早掐掉发现流量
version: "2026.06"
# 以下是我们的扩展键，别家解析器会忽略，不影响互通
x-ivyea:
  domain: amazon
  triggers: [launch, 新品, 冷启动, 自动广告, 测词]
  knowledge_ids: [playbook.launch_maturity_strategy, ...]
  tools: [knowledge_search, run_patrol, run_account_diagnosis, recall]
---
```

`x-` 前缀是通用的"私有扩展"约定，别家解析器遇到未知键会忽略。
`skill.json` 保留一个版本做兼容，**由 frontmatter 生成**，并加一条测试钉住两者一致；
下个大版本删除。

> **顺带的收获**：`skill.json` 里**本来就有 `tools` 和 `knowledge_ids`**。
> §4.1 说"frontmatter 新增 `tools` 字段"其实是**把已有能力搬个位置**，不是发明。
> 而 `knowledge_ids`（skill → 知识卡的显式链接）是我此前完全没利用的资产——
> 它能让 L3 路由不仅提升工具，还能预取该 skill 依赖的知识卡（§4.6 L3 增强）。

#### 为什么输出这一半才是战略价值

它把 IvyeaAgent 从"生态的消费者"变成"生态的供给方"——
一个做亚马逊运营的人可能先在 Claude Code 里用上你的 skill，然后才来装 IvyeaAgent。

这也正面回答了"开源自托管怎么获客"：**你的能力先于你的产品传播。**

### 7.3 DeepSeek Harness 兼容层：一个可选插件

**定位：`ivyea-cordis-host` 是一个可选插件。不装就不存在。**

#### 为什么只能是可选的

不是保守，是 §1.4 的硬性结论：

| 它要什么 | 与自托管约束的冲突 |
|---|---|
| Node 运行时 | 内核是纯 Python 3.9+、pip 可装 |
| npm 装一组 `@deepseek-ai/*` 包 | lockfile 风险（已有事故：内网镜像把 `resolved` 写死，用户机崩） |
| 内存开销 | 本机 dsh-web 被 systemd 限到 `MemoryHigh=600M / MemoryMax=900M`，且"必走 npm 包别源码构建，2vCPU 会 OOM" |

**开源自托管产品不能要求用户为了插件生态先装个 Node 环境。**

#### 技术上怎么做（如果要做）

实测一个真实社区插件（本机 `dshmarket@1.12.2`）的运行时硬依赖：

```jsonc
"peerDependencies": {
  "@deepseek-ai/cordis":       "^4.0.1",     // DI 容器
  "@deepseek-ai/dsh-settings": "^0.1.0-rc.7" // 它注入的那一个 seam
}
"dependencies": { "js-yaml": "^4.1.0" }      // 其余全是 Node 标准库
```

**两个包。不需要 dsh 本体、CLI、profile 或 web app。全部 MIT。**

且 Cordis 本身是独立第三方项目（作者 Shigma，即 Koishi 作者，
`package.json` 的 `repository.directory` 是 `vendor/cordis`），DeepSeek 是 vendor 进来用的。

所以 `ivyea-cordis-host` 的做法：**自己 boot 一个 Cordis 宿主，
seam 实现全是我们的**（`ctx.tools` 转发到 IvyeaAgent 的注册表，`ctx.llm` 转发到主脑，
`ctx.fs` 转发到文件层，`ctx.skills` 转发到技能根），再把社区插件装进去。

用户视角：**没有 dsh 命令、没有 dsh 界面、没有 dsh 品牌**，只有
`ivyea plugin add <社区插件>`。node_modules 里的包名不是"身影"——
判据是用户会不会知道它的存在，答案是不会。

#### 三条必须遵守的纪律

1. **版本 pin 死**，不用 `^`。（GBrain 那次全新装报 "No database URL"，
   根因就是没 pin，拿到了废掉 pglite 的新版。）
2. **先出兼容性测试台再谈兼容率**。批量装 top-100 插件，跑通率白纸黑字。
   **不实测就吹兼容率是耍流氓。**
3. **前端 UI 插件不做承诺**。那 279+72+72 个 ui/theme/fun 插件需要对方的
   client runtime + SlotRegistry + React。技术上可探索（那些也是独立 npm 包），
   但**排在工具类之后，且不写进任何对外承诺**。

#### 优先级

**放在最后一期，且是可选交付。** 前面所有期做完，IvyeaAgent 已经是一个
契约完备、生态双向、能自托管的产品；这一层是锦上添花，不是地基。

## 8. 市场

### 8.1 门道已有成熟实现，不新造

`/root/mendao/server/app/routers/market.py` 实测 **14 个端点**：

| 能力 | 端点 |
|---|---|
| 浏览 / 详情 / 版本 | `GET /skills`、`/skills/{slug}/detail`、`/skills/{slug}/versions` |
| **registry 分发** | `GET /index.json` |
| manifest / 下载 | `/skills/{slug}/{version}/manifest`、`/download` |
| 投稿 | `POST /submit`、`/submit-package` |
| **审核队列** | `GET /review-queue`、`POST /review` |
| 治理 | `/manage/skills`、`/manage/delist`、`/manage/remove`、`/manage/restore` |

SQLite 双表（`skills` + `skill_versions`），已有字段
`slug / version / sha256 / signature / manifest / scan_report / size_bytes / class / status`。

**这套东西已经能装插件了**——`manifest` 是自由 JSON，`class` 在做安全分级，
`scan_report` 在存扫描结果，`signature` 在做签名。

### 8.2 三方定位

| 角色 | 定位 | 要改什么 |
|---|---|---|
| **门道** | **上游 registry（权威）**：投稿、审核、分发 | 加 `type: skill\|plugin` 一列；`/index.json` 带上 type |
| **IvyeaOps 能力市场** | 消费端：浏览、本机安装 | `skill_market.py` 加 type 分支；插件安装展示 `permissions` 确认页 |
| **IvyeaAgent** | 安装目标 | 落盘到 `~/.ivyea/plugins/` 或 **`~/.agents/skills/`** |

**不抽 `ivyea-market-schema` 包**：只有一个生产者、一个消费者，抽包是过早抽象。
改成**门道的 `/index.json` 响应体就是契约**，用 `mendao/docs/registry-schema.json`
一份 JSON Schema + ops 侧契约测试钉住。

> 这和全案的纪律一致：**契约钉在真实消费方的响应上，不钉在想象的抽象层上。**

### 8.3 插件比 skill 多出来的审核项

`scan_report` 要扩：
- 声明的 `permissions`（网络域名 / 文件系统级别 / 是否含破坏性工具）
- **进程内（Python）形态的第三方投稿默认拒绝**——只接受协议型（§3.3）
- 依赖的其他插件 id 是否都在 registry 里

### 8.4 「能力市场」改名「市场」

不只是 skill 市场，也是插件市场。门道那边同理——因为它们是**同一个 registry 的两个视图**，
不是"长得像"。

## 9. 插件的用户体验

> 对一个靠第三方插件的开源自托管产品，**装 / 卸 / 管本身就是产品**。
> 契约再好，装一个插件要读文档才会，生态就起不来。

### 9.0 原则：扩展现有的 skill 安装流程，不新造

IvyeaOps 的 `skill_market.py` 已经有一套设计得很扎实的安装流程，**直接沿用**：

| 已有机制 | 原文注释里的理由 | 插件是否沿用 |
|---|---|---|
| **`preview → confirm_token → install` 两阶段** | "没看过清单就装不了" | ✅ |
| **`confirm_token = sha256(blob)`，install 时核对** | "防止看的是 A、装的是 B" | ✅ |
| **本地二次分析 `analyze()`** | "门道那边判能不能上架，这里判要不要让它落到我这台机器上。市场源是可以换的，所以这一步不能省" | ✅ 且扩充插件专属检查项 |
| **署名带到确认弹窗** | "用户在决定装不装的那一刻，就该知道这东西是谁写的、什么许可证" | ✅ |
| **卸载走回收站不直接删** | "误删一个改过的 Skill 是能挽回的" | ✅ |
| **安装账本记 source + sha256** | "某个 skill 被市场下架时，能立刻查出本机装没装" | ✅ |
| **`is_relative_to` 做路径穿越检查** | Windows 反斜杠让字符串前缀检查恒为假 | ✅ 照抄，别用 startswith |
| **`audit.record` 审计** | — | ✅ |

### 9.1 插件比 skill 多出来的四件事

skill 是一份**静态文本**；插件是**活的**。所以插件的 UX 必须多覆盖：

| # | 差异 | 带来的 UX 需求 |
|---|---|---|
| 1 | 插件有**进程和状态**（会崩、会连不上） | 运行状态可见 + 失败原因可见 + 重试 |
| 2 | 插件有**权限**（网络 / 文件 / env / 破坏性工具） | 授权页 + 装后可调整 |
| 3 | 插件**贡献多种东西**（工具 / 技能 / 面板 / 钩子 / 子代理） | "它给了我什么"要一眼看清 |
| 4 | 插件可能是**排障对象**（"是不是它搞的鬼"） | **禁用**（不卸载）+ 日志 |

### 9.2 安装：三条路径，一个流程

| 路径 | 面向 | 入口 |
|---|---|---|
| **市场点装** | 普通用户（主路径） | ops 能力市场 / 自带 web 的插件页 |
| **CLI** | 开发者 / 自动化 / 无 web 的自托管 | `ivyea plugin install <slug\|路径\|URL>` |
| **手动放目录** | 离线 / 内网 / 气隙环境 | 解压到 `~/.ivyea/plugins/<id>/` 后 `ivyea plugin refresh` |

三条路径**共用同一套校验**（完整性 → 本地分析 → 权限确认 → 落盘 → 抓工具目录 → 记账本）。
CLI 的 `--yes` 只跳过交互，**不跳过校验**。

#### 安装确认页要展示什么

比 skill 多的部分**加粗**：

```
┌─────────────────────────────────────────────────────┐
│  快递查询  v1.2.0                                    │
│  作者 zhangsan · MIT · 来自 门道社区 · A 类           │
│  完整性 ✅ sha256 匹配 · 签名有效                     │
├─────────────────────────────────────────────────────┤
│  **它会给你什么**                                    │
│    工具 3 个   查快递单号 / 批量查询 / 订阅物流更新    │
│    技能 1 个   物流异常排查                           │
│    面板 0 个                                          │
├─────────────────────────────────────────────────────┤
│  **它需要什么权限**                                  │
│    🌐 网络   api.kuaidi100.com                       │
│    📁 文件   不访问                                   │
│    🔑 环境   KUAIDI100_KEY（需你稍后填写）            │
│    ⚠️ 含 1 个破坏性工具：订阅物流更新                 │
├─────────────────────────────────────────────────────┤
│  ℹ️ 首次安装只授予**只读**权限。破坏性工具需要你       │
│     之后在插件管理里单独放行。                        │

└─────────────────────────────────────────────────────┘
```

**"它会给你什么" + "它需要什么权限"这两栏是信任的全部。**
其中"工具 3 个"的名字来自 §4.7c 的工具目录——**安装时抓一次，正好在这里用上**。

#### 装完不能只弹一个 toast

装完要给一张**变化清单**，并把下一步动作放在手边：

```
✅ 已安装 快递查询 v1.2.0
   新增 3 个工具、1 个技能
   ⚠️ 1 个工具（订阅物流更新）标记为破坏性，当前未授权
   ⚠️ 需要配置 KUAIDI100_KEY 才能使用

   [去配置]  [试用一下]  [授予完全权限]  [查看详情]
```

"试用一下"直接开一个会话并预填一句 `帮我查一下快递 SF1234567890`——
**让用户在 10 秒内看到它真的работ**，这是留存的关键一步。

### 9.3 管理页

一张表，回答"我装了什么、活着吗、给了我什么、要不要动它"：

| 插件 | 版本 | 状态 | 贡献 | 权限 | 操作 |
|---|---|---|---|---|---|
| IvyeaOps 板块能力 | 1.1.116 | 🟢 运行中 | 48 工具 · 1 面板 | 完全 | 禁用 · 权限 · 详情 |
| 快递查询 | 1.2.0 | ⚪ 未连接 | 3 工具 · 1 技能 | 只读 | 禁用 · 更新 · 权限 · 卸载 |
| 某某插件 | 0.3.1 | 🔴 加载失败 | — | — | **查看原因** · 重试 · 卸载 |
| 旧插件 | 1.0.0 | 🟡 已禁用 | 2 工具 | 只读 | 启用 · 卸载 |

四种状态的语义：

| 状态 | 含义 |
|---|---|
| 🟢 运行中 | 已连接，工具可用 |
| ⚪ **未连接** | 正常态！§4.7c 的懒连接——工具目录来自缓存，首次调用才 spawn。**不是错误，UI 不能显示成告警** |
| 🔴 加载失败 | 附**可读的**原因（"命令不存在: kuaidi-mcp"、"启动超时 30s"、"契约版本 2 高于内核支持的 1"）+ 重试 |
| 🟡 已禁用 | 文件和配置都在，只是不加载 |

### 9.4 禁用 ≠ 卸载（排障的第一手段）

用户遇到"agent 最近怪怪的"时，第一反应应该是**逐个禁用插件试**，而不是卸载重装。

- **禁用**：文件留着、配置留着、账本留着，只是不加载。一键可逆
- **卸载**：文件进回收站，账本移除，**数据默认保留**

```
ivyea plugin disable <id>     # 排障用
ivyea plugin enable  <id>
```

管理页提供一个**"安全模式"**开关：一键禁用全部第三方插件（自带件不动），
用来快速判断"问题是不是插件带来的"。

### 9.5 卸载

卸载前告知影响，卸载后处理残留：

```
确认卸载 快递查询 v1.2.0？
  将移除：3 个工具、1 个技能
  ☐ 同时删除该插件的数据（配置、缓存）        ← 默认不勾
  插件文件将移入回收站，30 天内可恢复
                              [取消]  [卸载]
```

**数据默认保留**的理由和 skill 走回收站是同一条：**误删是能挽回的才叫好设计。**
重装同 id 插件时，若发现残留数据，提示"检测到上次的配置，是否恢复"。

技术上必须保证：卸载 = 逆序执行该插件的全部 disposer（§4.9），
工具 / 技能 / 面板 / 钩子**当场消失**，不需要重启。
`ivyea plugin test` 里那条"检查 disposer 清干净"就是在守这个（§4.9）。

### 9.6 失败态：不许静默

三条硬规则：

1. **插件加载失败不阻断启动**（§4.9）。内核降级继续跑，管理页红点，`/v1/plugins` 可查
2. **工具调用出错必须带 plugin_id**。错误文案是
   `工具 kuaidi_query 执行失败（来自插件「快递查询」）：连接超时` ——
   而不是一句 `工具执行出错`。**用户要能一眼知道该找谁**
3. **每个插件有独立日志**：`~/.ivyea/plugins/<id>/logs/`，管理页可直接看，
   `ivyea plugin logs <id>` 可 tail

### 9.7 市场：从「能力市场」到「市场」

一个页面两个标签，共用 registry（§8）：

```
市场
├── 技能   （现有，不动）
└── 插件   （新增）
     筛选：分类 · 来源 · 已安装 · 有更新
     卡片：名称 · 一句话 · 作者 · 星标 · 类别徽章(A/B) · [安装/已安装/更新]
```

**插件卡片比 skill 卡片多两个徽章**：
- **贡献徽章**：`3 工具` `1 技能` `1 面板` —— 不点进去就知道它是干嘛的
- **权限徽章**：`🌐 联网` `⚠️ 含破坏性操作` —— 危险性前置，不藏在详情页里

**有更新时**：管理页和市场页都显示 `1.2.0 → 1.3.0` 的角标，
点更新走 §4.8c 的流程（装新版 → 跑 test → 通过才切 → 失败自动回滚）。

### 9.8 自托管特有的四件事

| 场景 | 设计 |
|---|---|
| **离线 / 气隙** | `ivyea plugin install ./kuaidi-1.2.0.tar.gz`；市场页支持"导出安装包"给别人 |
| **内网市场** | 市场地址可配（ops 已有 `market_url()` / `hub_settings`），可指向自建 registry |
| **Windows** | 路径用 `Path.is_relative_to` 不用字符串前缀（ops 已踩过这个坑）；插件目录用 `current.txt` 记版本不用符号链接（符号链接要管理员权限）；hook 支持 `command_windows` |
| **没有 web 的部署** | 全部能力有对等 CLI：`install/uninstall/enable/disable/update/list/info/logs/refresh` |

### 9.9 这些落在哪一期

| 交付 | 期 |
|---|---|
| CLI 全套（install/uninstall/enable/disable/list/info/logs/refresh） | **P0** |
| 工具目录抓取（喂给确认页的"它会给你什么"） | **P0** |
| 每插件独立日志 + 错误带 plugin_id | **P0** |
| 自带 web 的插件管理页（状态 / 禁用 / 卸载） | **P3** |
| ops 市场的插件标签 + 确认页 + 徽章 | **P4** |
| 更新流程 + 有更新角标 | **P4** |
| "安全模式"一键禁用全部第三方 | **P4** |

> **P0 就要有完整 CLI** 的理由：P1 装第一个插件（ivyea-ops）时，
> 我们自己就是第一个用户。**自己都得靠手改目录才能装，别指望别人来写插件。**

## 10. 影响面与风险

### 10.1 进程边界（最关键的决定）

生产现状：`ivyea-ops.service`(:8001) 与 `ivyea-agent.service`(:8765) 各自 systemd 托管。
**本方案不改变这个拓扑。** 理由见 §6.3。

### 10.4 回归防护：这套改造会不会把现有功能弄坏

> 这一节的每个数字都是**实测**，不是估计。

#### 10.4.1 基线（2026-08-22 实跑）

```
$ python3 -m pytest tests/ -q
1199 passed, 1 skipped in 66.01s
```

- 测试文件 **132** 个，**18,584 行**，用例 **1200** 个
- **全绿，零既有失败**
- **66 秒**跑完 —— 快到可以每改一次就跑一遍，不需要攒着

> 对照：`ivyea-ops` 有 **16 个既有失败**（用例间污染，单独跑全过）。
> 意思是**动 agent 比动 ops 安全得多**——agent 的安全网是完好的，
> ops 那边得先分清哪些失败是自己弄的。P1 涉及 ops 时必须先 `git stash` 钉基线，
> 且那个 16 需要在实施时**重新确认**（可能已变）。

#### 10.4.2 全部改动按"能不能弄坏现有功能"分类

**A 类 · 纯加法（物理上不可能坏）——约占工作量的 80%**

| 改动 | 为什么安全 |
|---|---|
| `~/.agents/skills` 加扫描根 | 多一个来源，老的 `~/.ivyea/skills` 原样工作 |
| 内置 skill 补 frontmatter | `skill.json` 仍优先，加载路径不变 |
| 门面层 JSON-RPC | **新入口**，既有 100+ 个 `/v1/*` 端点一行不改 |
| `/v1/plugins`、插件 CLI、`ivyea-web` | 全新的东西 |
| `permission_request` hook | 新事件，没配就是零开销（沿用 `hooks.enabled()` 的既有设计） |
| 工具目录缓存、配置分层、独立日志 | 新机制 |
| ops 补 `readonly`/`parallel_safe` + manifest 端点 | 加字段，老消费方不受影响 |
| 补齐 5 个板块工具 | 纯新增 |

**B 类 · 真正动到主路径的只有 3 处**

| # | 改动 | 血脉级别 | 实测覆盖 |
|---|---|---|---|
| B1 | `TOOL_SCHEMAS`/`_DISPATCH` → `ToolRegistry` | 🔴 54 个工具全走这里 | ✅ **46/132 个测试文件**直接摸这条路 |
| B2 | `dispatch_result` 权限裁决上提 | 🔴 错了要么该拦不拦、要么不该拦却拦 | ✅ **9 个** permission 测试 + 上面 46 个 |
| B3 | **环境变量清洗**（§4.7b） | 🔴 自带件分支写错，MCP 和 hook 立刻全挂 | ⚠️ **见下，这是精确软肋** |

#### 10.4.3 精确软肋：env 传递零断言

先纠正一个容易下错的判断：hooks 看起来"只有 1 个测试文件"，
但实测 `tests/test_commands_and_hooks.py` 里 **15 个用例中 11 个是 hooks 的**，
覆盖 `fire` / `fire_decision` / matcher 正则 / 阻断 / fail-open / 旧格式兼容 /
与 `dispatch_result` 的集成。MCP 侧也有 3 个文件 **23 个用例**。
**行为覆盖是够的。**

真正的缺口很窄，但正好落在 B3 上：

```
断言 hook 收到什么环境变量的测试：0
断言 MCP 子进程 env 的测试：      0
```

**意思是：如果我把环境隔离写错了，现有 1199 个测试会全绿。**
因为没有一个用例检查子进程实际拿到了什么。

#### 10.4.4 由此得出的顺序约束（写进 P0 的施工顺序）

```
① 先补测试：断言 hook 与 MCP 子进程收到的 env（三种来源各一例）
      ↓  此时测试应该「按现状全绿」——它们钉住的是今天的行为
② 再改代码：实现 §4.7b 的三层隔离
      ↓  自带件那例必须仍绿（零回归），另两例应转为「拿不到密钥」
③ 最后加对抗用例：装一个会 `env | grep -i key` 的测试插件，验证取不到东西
```

**顺序不能反。** 先改代码再补测试，等于用改完的行为定义"正确"，
那测试就只是在给既成事实背书。

同样的顺序适用于 B1、B2：**先给现状加钉子，再动。**

#### 10.4.5 测试接不住的两类

诚实说，1199 个绿灯不等于万无一失：

**① P2 的工具路由是「行为改变」，不是「功能损坏」**

功能一个不少，但模型看到的工具集变了——可能选得更准，
也可能在某些场景下少挂了本该挂的工具。
**这是全案唯一会让你感觉"变了"的一期。** 已有的护栏：
- 工具选择准确率评测不低于基线（P2 验收）
- 三级路由各自可单独关闭，一键退回"全挂"模式（= 改造前行为）

**② 生产环境特有的东西**

systemd 托管、Windows、ops 联动、真实 LLM 行为——本机测试覆盖不到，
靠分期上线时逐项实测。所以 P1 的验收写的是"48 个板块能力**逐个实测调通**（不抽样）"。

#### 10.4.6 三层兜底

1. **P0 验收是"逐字节一致"**——未装任何插件时，`ivyea chat` 和 serve 的行为
   必须与 v1.15.6 完全相同。这不是"差不多就行"，是可比对的
2. **每期独立可回滚**，且 B1 的 `TOOL_SCHEMAS` 重构**单独一个 commit**，出事 revert 那一个
3. **66 秒全量测试** + 每期结束跑一次基线比对

#### 10.4.7 施工检查清单

每次动 B 类改动前后各过一遍：

- [ ] 动手前跑一次全量，记下基线（`1199 passed` 或当时的实际数）
- [ ] B 类改动**先补钉子测试**，确认「按现状全绿」
- [ ] 改完全量必须**回到基线数**，多一个失败都要查清楚，不许"这个本来就不稳定"
- [ ] B1/B2/B3 各自**单独 commit**，不与其他改动混在一起
- [ ] 涉及 ops 时先 `git stash` 钉 ops 侧基线（那边有既有失败）
- [ ] 期末做一次"逐字节一致"比对（未装插件时的 CLI/serve 行为）

- 破坏性工具审批卡正常弹出，拒绝生效
- ops 全量 pytest 与 **16 个既有失败的基线**一致

**回滚**：agent 侧保留旧代码路径一个版本，feature flag 切换

### P2 — 工具路由（解决 R1，**接第二个插件前的硬门槛**）

**交付**
- L1 门面折叠（从 ops 专用泛化）
- L2 语义提升（新建，建在 `onnx_embedding` + `retrieval_embeddings` 上，与 `routing.py` **串联**）
- L3 skill 引路（frontmatter 加 `plugins`/`tools`）
- skill 渐进披露（元数据 ~8KB 上限）
- 评测：扩 `evals.py`，加"工具选择准确率"用例

**验收**
- 98+ 工具规模下，prompt 工具部分 token **不超过** 54 工具时的 6.9K
- 工具选择准确率**不低于**改造前基线
- 三级路由各自可单独关闭

**回滚**：降级到"全挂"模式（= 改造前行为）

### P3 — 门面层 + Web 插件 + UI 契约

**交付**
- **门面层**：JSON-RPC 2.0 入口——**stdio 必须是独立子命令 `ivyea app-server`**
  （§4.7e ②，否则与 `ivyea chat` 抢 stdin/stdout），HTTP 走 `/rpc`；映射表见 §5.2；
- **动手前先查**：现有会话 messages 里有没有留每轮 usage（§4.7e ③）——
  没留的话 `thread/rollback` 只能把 usage 标为"已失真"，不能给个错的数
  补 `turn/interrupt`、`turn/steer`、`thread/fork`、`thread/rollback`、
  `thread/archive`、`thread/name/set` 6 个方法
- **反向审批请求**：`execCommandApproval`/`applyPatchApproval`，
  复用现有 `permission.prompt_fn` 通道
- **多客户端审批归属**（§4.7d）：请求带 `thread_id` + `origin_client_id`，
  谁发起谁决策，其余客户端只读可见；`pending` 端点加 `client_id` 过滤（不传时保持全量，向后兼容）
- **`ivyea-web`**：自带前端作为 UI 插件（原生 ESM，无构建）
- **UI 槽位契约**落地（§4.5），支持 `entry` 与 `iframe` 两种
- **任务台走快路接入**：`iframe` 指向 ops 任务台，验证 UI 契约

**验收**
- 用现成的 Codex app-server 客户端（官方 Python SDK 或第三方）**实测驱动 IvyeaAgent**
  ——这是"对齐"是否成立的唯一判据，不实测不算数
- ADR-0005 的可靠性回归用例全绿（R7）
- `ivyea web` 断网可起、可对话、可审批
- 任务台面板在自带 web 里可用

## 12. 优先级建议

| 期 | 规模 | 风险 | 说明 |
|---|---|---|---|
| **P0** 契约与内核 | 中 | 中 | 地基。LICENSE 那条可以今天就做 |
| **P1** ops 插件化 | 中 | 低 | P0 的压测——用现成 48 个工具把契约压透 |
| **P2** 工具路由 | 中 | 中 | **硬门槛**，不做完不许接第二个插件 |
| **P3** 门面 + Web | 中 | 中 | 生态价值最高的一期：现成客户端能驱动你 |
| **P4** 市场 + subagent | 中 | 低 | 三仓库联动，门道先动 |
| **P5** Cordis 兼容 | 大 | 中 | 可选，最后 |

**如果只能做三件事**：P0 + P1 + P2。
它把"加一个能力要改内核源码"变成"加一个 manifest"，并解决工具爆炸这个唯一的技术死穴。

**如果想最快看到生态回报**：P0 里的 `~/.agents/skills` 那一行改动
——**改完当天，你的 skill 就能被 Claude Code / Codex / dsh 用上**。
这是全案投入产出比最高的一处。

## 13. 待拍板

1. **门面层的 JSON-RPC 是否 P3 就做全 6 个方法？**
   建议：做全。`turn/interrupt`/`turn/steer` 本来就是任务台需要的（§6.3.2），
   两件事是同一件事，分开做等于做两遍。

2. **任务台走快路（iframe）还是深路（子树搬迁）？**
   建议：**P3 快路，深路等 UI 契约验证后再评估**。快路当天可用且零改造。

3. **`brain` 板块的写入类能力开不开给 agent？**
   建议：**只开只读检索**。绕过 ops 的知识审核链等于拆掉已建好的质量闸门。

4. **P5 的 Cordis 兼容层做不做？**
   建议：**P0~P4 做完再定**。那时 IvyeaAgent 已经是契约完备、生态双向的产品，
   再看那 1837 个插件值不值得引入 Node。**现在就承诺等于给自己上枷锁。**

5. **LICENSE 用 MIT 吗？**
   建议：MIT，与 ivyea-ops 一致。这条不依赖任何其他决策。
