# ADR-0038：注入精度优先于召回率，且必须先能度量

- 日期：2026-09-02
- 状态：已采纳

## 背景

用户报告 agent "偶尔引用毫不相关的技能、知识库"，并怀疑根因是"接到指令的第一步没有
思考，直接触发了某些检索"。查下去，这个判断是对的：一轮的顺序是

```
用户的话 → 知识检索 / 技能匹配 / 记忆召回（三路并发、无条件、拿原话当 query）
        → 结果拼进上下文 → 模型这时才第一次看到东西
```

判断"要不要查""查什么""这条相不相关"的全是规则，不是模型。规则只看到"图片"两个字，
它不知道这句话在说前端 bug。

在真实库上复现出三路各自的失败：

| 查询 | 误注了什么 | 为什么 |
|---|---|---|
| 版本号写在哪个位置 | `reference/DeepSeek harness 凭据配置位置` | 只对上"位置" |
| 把改动推送合并发版 | `console 双卡合并口径` | "合并"是另一个意思 |
| 给 ivyea-agent 加功能 | 一堆 ivyea-note 的记忆 | 对上"ivyea" |
| 帮我看下这个图片点不开的问题 | `amazon.listing_image` 等两份审计手册 | 对上"图片" |
| 亚马逊图片怎么优化 | 同一篇长文的三张切片 | 一篇文章被上传了三次 |

还有一个恶性循环：遗忘打分只认"被检索命中"，误召同样加分。harness 那条因此 hits=4、
最近命中就是今天，在打分里排到**全库第一** —— 用户几天没碰它，它反而越站越稳。

## 决定

### 一、先立度量，而且指标是双向的

`memory_eval` 只测 recall@k，`knowledge_quality` 只测"该给的证据给了没有"。整套检索
从来没有被"不该注的有没有注"考核过。新增 `tests/test_injection_precision.py`：三路的
**负例**用例，全部来自真实翻车案例，进默认测试套。

**误注率是硬指标，但漏检率同等重要** —— 否则"什么都不注"会拿满分，那是更糟的失败。
所以负例集里同时钉着"该召回的必须召回"。

用例**自带数据**，不读开发机上的真实库：CI 上那个库是空的，空库当然不会误注，整批
负例会变成假绿。第一版就是这么写的，跑全量时才暴露（单跑全绿、混跑挂）。

### 二、词法命中要看"重合的是什么词"，不是"有没有重合"

新增 `textseg.strong_overlap`：判据是**至少一个强信号词重合**。强信号 = 三层都过：

1. 不是虚词碎渣（`STOP_GRAMS`，从 `skills` 提到词法层 —— 记忆那条路同样需要）；
2. 不是**语言层弱信号词**（`WEAK_TERMS`：位置/配置/合并/图片/分析/功能…）——
   它们是实词，但单独出现时不说明这句话是关于什么的；
3. 不是**这个库的万能词**（DF ≥ 30%：记忆库里 ivyea 占 86%、note 57%）。

两层缺一不可：实测「位置」只出现在 14% 的记忆里、「合并」7%，光靠 DF 挡不住；而
「图片」在技能库只占 15%、在记忆库一次都没出现，只能靠 WEAK_TERMS 兜住。

另外，中文按 2-gram 切会产生"话的""的功"这类跨词边界碎片，一律不算信号。

### 三、领域闸要两条路一致

"工程任务不注亚马逊知识"这道闸 CLI 一直有、**serve 一直没有**，而工作台走的正是
serve。同一句"图片点不开"在终端被挡掉、在工作台照注。现在 serve 复用 `chat_ui` 的
同两个函数，不另写一套。判据本身也补齐了界面/交互故障那一类词（点不开、白屏、渲染、
配置文件…）—— 放在这里是安全的：调用方的判据是 `亚马逊信号 or 不像工程任务`，
真正的运营问题在前半句就放行了。

### 四、同一份材料在一次召回里最多占一席

要治的是"同一篇长文被重复上传、切成多张近似卡霸榜"。判据经过两轮收窄，**别再放宽**：

* 不能按 `source_url` 归组 —— 两张讲不同事的官方卡合法地共享同一个帮助页
  （`policies.ip_complaint_evidence` 和 `policies.intellectual_property_policy` 都出自
  G201361070），归到一起会删掉其中一张；
* 不能按标题**前缀**归组 —— 官方卡标题成系列，"Sponsored Products report…" 和
  "Sponsored Products bidding…" 前十几个字一样，按前缀判会把讲竞价的那张当重复删掉。

最终只认一种情形：上传类卡（`ivyea-upload://`）且**完整标题相同**。

这两个边界都不是想出来的，是既有的 `knowledge_quality` / `test_knowledge_base` 门禁
打出来的 —— 没有先立度量那一步，这两个错会直接上线。

### 五、误召要有反向通道

新增 `memory_decay.record_irrelevant`：扣掉那一次不该记的命中、记一笔 `misses`，
打分时按次数打折（乘法不是减法：说过一次"不相关"只该让它退一步，不是判死刑）。

出口是**界面上顺手点一下**：每轮"回忆了哪几条"本来就画在活动行里，每条后面挂一个
"×"。靠人翻日志找误召不可能长期做下去，而这一行就在眼前。这是负例集唯一可持续的
供货渠道。

## 明确不做的两件事

写下来免得以后又被"修掉"：

1. **`user.*` 知识卡不降池。** 它们的 `source_quality` 是
   `account_local_overrides_generic_knowledge` —— 账户本地经验本来就该压过通用知识。
   第一版方案里"把 user 卡降为只有 knowledge_search 可达"是错的。
2. **`governance.professional_knowledge_standard` 出现在证据里是故意的。**
   `_ensure_evidence_standard` 在"一张权威卡都没命中、手里只有用户长文"时会主动挂上
   这张护栏卡 —— 那正是最容易顺着问题编的情形。它出现说明护栏在工作。

## 索引层：类别饥饿（补记）

原计划的最后一步是"把索引层换成类别+计数，让模型自己去查"，理由是"索引层 O(n)、
记忆长大后每轮十几 K token"。核实之后这个理由**不成立** —— `MAX_INDEX_CHARS = 3000`
早就在那儿，索引层一直是有上界的。

但造一个 133 条的库跑出来，暴露了另一个真缺陷：预算是按 `CATEGORIES` 的顺序**先到
先得**的。project 有 120 条，它吃掉大半预算，排在最后的 domain（6 条运营打法）
**一条都没露出来**。也就是说，随着项目记录变多，"可复用的打法"会安静地从模型眼前
消失，而且没有任何迹象 —— 用户只会觉得"它怎么把以前的结论忘了"。

改成两轮发预算：先给每类留 `RESERVED_PER_CATEGORY = 4` 个保底名额，剩下的再按原顺序
补。同一个库上 domain 从 0 条回到 5 条，project 从 56 让到 53。五个类别全占满也才 20 行，
占不到预算三分之一。

连带两处：

* **反思用全量索引**（`REFLECTION_INDEX_CHARS`）。它靠目录判断"这条已经有了，该
  update 不该 add"，看摘要版会重复建记忆 —— 碎片化正是这套东西最怕的失败方式。
  它一天最多跑几次，多花 token 换不碎片化划算。
* **系统提示不再谎称目录是全的**。原话是"列出每条记忆的名字和一句话描述"，模型据此
  以为看到的就是全部，于是不会去查目录外的东西。现在明说"只列了一部分，没出现在
  目录里不等于没有，拿不准就 memory_search 查一次"。

## 没有做的那一半：停掉盲注入、改成模型自取

原方案里这是最后一步，也是风险最大的一步（每轮多一次往返）。做完前面几步之后
**收益变得不明确**：强信号门槛上线后，三路的误注负例已经全绿，而"模型自取"要解决的
正是误注。在误注率已经归零的情况下，用一次确定的往返去换一个不确定的改善，不划算。

它仍然是对的方向 —— 规则永远不会理解"图片点不开"是前端 bug，而模型会。但要动它，
应该先让现在这套跑一段时间，用第五节那个反向通道收集**真实的**误召样本；如果强信号
门槛之后还有一批规则挡不住的误注，那才是切架构的依据。没有那批数据就动，等于重复
这套系统栽过两次的老路。

## 影响

- 三路的误注用例从 9 红 → 全绿，漏检用例保持绿。
- `chat` / `quick` / `board` / `work` 四条 lane 的行为不变。
- 下一步（让模型自己决定检索什么，而不是规则预取）风险高得多，要在这套度量建起来之后
  再切，且带开关灰度。
