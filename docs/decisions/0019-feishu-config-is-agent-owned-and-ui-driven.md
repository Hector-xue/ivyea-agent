# ADR-0019 · 飞书配置归 agent 存，界面来写；relay 以它为准，env 只兜底

- **日期**：2026-08-23
- **状态**：已采纳
- **相关**：ADR-0017（巡检与审批闭环）、IvyeaOps 的 ADR-0024（同一件事在 ops 那边的记录）

## 背景

飞书这套东西落地后，同一个飞书应用的凭据散在三处：`~/.ivyea/.env`（agent 发卡片）、
`/etc/feishu-ivyea-relay.env`（relay 收回调）、IvyeaOps 的 `hub_settings.json`
（CPU 告警）。三处互不知情，漏配任何一处的表现都一样：**保存成功、也不报错、
就是收不到消息**。审批白名单更麻烦——它只在 relay 的 EnvironmentFile 里，
改一次要 SSH 上机器编辑再重启服务。

而这套东西是要开源发出去给别人用的。让用户 SSH 进去编辑三个文件才能用上核心功能，
等于这个功能不存在。

## 决策

### 一、agent 侧新增配置端点，凭 IvyeaOps 界面驱动

`GET/POST /v1/config/feishu` + `POST /v1/config/feishu/action`（列群 / 列成员 /
发测试卡片 / 配巡检任务）。沿用 `/v1/config/vision` 的成例：**ops 不直接碰
`~/.ivyea`**，一律走端点，agent 自己决定什么落 settings、什么落 .env。

### 二、凭据写文件的同时写进程环境

`config.load_env()` 明确"不覆盖已存在的环境变量"，而 serve 是常驻进程。只写 .env
的话，界面显示新凭据、发出去的还是旧应用——典型的假开关。所以 `configure()`
两处一起写，并顺手删掉缓存的 tenant token（换了应用还留着旧 token，下一条消息
就以旧身份发出去了）。

### 三、白名单挪进 `settings.json`，relay 以它为准

`feishu_allowed_senders` / `feishu_allowed_chats`。relay 改成
**agent 配置优先、环境变量兜底**，且每次判定都现取，不用启动快照。

### 四、配巡检任务时收编同类旧任务

界面上开一条全店巡检，会先清掉所有 `store_*` 任务再按界面重建，并如实回报清掉了谁。

## 理由

**为什么 relay 是"文件优先、env 兜底"，与常规习惯相反**：常规是 env 覆盖文件，
因为 env 通常代表"这次部署的特殊情况"。但这里覆盖的是**撤权**：在界面上把某人从
审批白名单里删掉，界面上没了、保存也成功，relay 却还认着 env 里的旧名单继续放行。
配错顶多发不出消息，撤权失败是真会花钱的。所以让能在界面上改的那一份说了算。

**为什么"空列表"必须区别于"没配"**：空白名单是一条有意义的配置（谁都不许点），
不是"这项还没填、去读 env"。判定按**键在不在**，不按值真不真。

**为什么收编旧任务而不是并存**：并存的结果是同一个店被巡两遍、飞书里出现两张几乎
一样的卡。合并规则再怎么调也救不了——那是两条独立任务各自推的。

**为什么 relay 启动不再硬性要求白名单**：白名单现在能在界面上随时改（不重启即生效），
再拿它当启动条件就是死结——新用户填完凭据想先起 relay 试试对话，却因为还没指定
审批人而起不来。安全性没下降：`gates.sender_allowed` 里空名单依旧拒绝所有人，
这里只是把它降级成一条醒目的启动警告。

## 后果

- 老部署（只有 EnvironmentFile、从没用过界面）行为不变：settings 里没有那两个键，
  自动回退到 env。
- 单测必须用 `IVYEA_HOME` 隔离——relay 的白名单解析会读 `~/.ivyea`，
  常量写死路径的话，单测读的就是这台机器上真实的审批白名单。已在
  `tests/test_config_source.py` 里守住。

## 实测记录（同日，真实应用）

- `im/v1/chats` 返回 `code=0` + 空 items，尽管机器人确实在群里、卡片也发得进去。
  它只列"应用可管理"的群。**空列表是正常结果，不是故障**，界面必须同时支持手工粘
  `oc_` 开头的 chat_id。
- `im/v1/chats/{id}/members` 正常返回成员 `open_id` 与姓名，审批人因此可以勾选。
