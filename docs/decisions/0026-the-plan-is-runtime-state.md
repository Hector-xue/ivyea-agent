# ADR-0026：计划是运行时状态，不是模型的记忆

- 日期：2026-08-28
- 状态：已采纳

## 背景

多步任务的计划此前只有一个载体：`ToolContext.todos` —— 一个内存列表，由模型调
`todo_write` 维护，`progress_reporting` 那套汇报状态机拿它做校验。

它有三个说不通的地方：

1. **它从来没有被注回模型的上下文。** 模型之所以"知道"自己的计划，全靠它自己那几条
   `todo_write` 工具调用还留在消息历史里。这是**模型自己记得**，不是**系统告诉它**。
2. **压缩会把它抹掉。** `/compact`（以及轮内防溢出压缩）把旧历史整段换成一段散文摘要，
   那几条 `todo_write` 调用随之消失。模型接着干活时已经不知道自己原本打算干几件事、
   干到第几件了 —— 而这恰恰发生在长任务最需要计划的时候。
3. **它掉电即失。** 进程重启、会话续跑、任务台接管，计划都不在了。与此同时
   `task_runner` 已经在 `~/.ivyea/tasks/*.json` 里存着一份**另一套**步骤表
   （`task_step` 维护），两套并行、互不知情。

这与记忆此前踩的是同一个坑，见 [ADR-0025](./0025-memory-is-runtime-driven.md)：
**指望模型"记得自己说过什么"的机制，迟早会在它最该记得的时候失灵。**

## 决策

**计划升格为运行时状态，由 `plan_store` 持有并每轮回注。**

- 落盘 `~/.ivyea/plans/<session>.json`：目标、范围、完成标准、每步状态与证据、
  批准戳、修订历史。
- `todo_write` 写台账、再同步回 `ctx.todos`；`ctx.todos` 降级为缓存。汇报状态机
  一行不改。
- 每轮由运行时把 `[当前计划]` 注回最后一条 user 消息（与 `task_scope` 的范围契约
  同一个机制、同一个位置）。
- **压缩时计划原样穿过**：`context.compact` 新增 `extra_note`，把计划接在摘要之后。
  摘要是散文、会走样；"干到第几步"是状态，不能交给模型复述。

配套两条：

- **`loop_guard`**：同一 (工具, 参数) 重复 N 次、或连续 M 步没有新证据，就拦下来并
  给计划打上重规划标记。原地打转不是"工具失败"，此前一条守卫都不管它。
- **行为门禁只认真代码**：`write_file` 写了一份 `.md` 不该被要求"跑一遍真实运行路径"。

## 为什么不选另外两条路

**A. 从消息历史里回捞 todo（hermes 的做法）。** hermes 在 `run_agent.py` 里专门写了
一段：倒着扫历史，找最近一条 `todo` 工具结果，把状态恢复出来。这条路能修"模型忘了"，
但修不了"历史被压掉了"—— 压缩之后那条工具结果根本不在了。而压缩恰恰是长任务的常态。
回捞是在**已经丢失的载体上**做补救，落盘是换一个不会丢的载体。

**B. 把计划塞进 system prompt。** 试过就知道不行：Anthropic 那条路的 `_split_messages`
会把 system 单独切出去，多条 system 各家 provider 行为不一致。追加到最后一条 user
消息是所有 provider 都保真的做法，`task_scope` 的范围契约早就在这么干了。

## 代价与边界

- **多了一份磁盘状态。** 换来的是压缩/重启/续跑之后计划还在。文件损坏一律当作"没有计划"，
  绝不让一个坏文件把对话卡死。
- **每轮多几百 token 的常驻上下文。** 只在有多步计划时才注入，`_NOTE_MAX_CHARS` 封顶。
- **没有 session_id 就整个模块空转。** 只读子 agent、单元测试里的裸 `ToolContext` 属于
  这一类，它们的行为与改造前逐字相同。
- **批准闸只对"真的走过计划模式"的会话生效。** 普通对话不会凭空多出一道闸 ——
  这是硬要求，不是权衡。
- `loop_guard` 豁免轮询类（`bash_output`）与记账类工具：前者同参数反复调用是正确用法，
  后者本来就该重复出现。把它们算进去等于自找误报。

## 还没做

计划台账与 `task_runner` 的双向对接（消除两套步骤表示）留到下一期；当前 `plan_store`
已经记下 `task_id`，接线时不需要改数据结构。
