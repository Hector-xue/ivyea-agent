# ADR-0009 · 技能改用通行的 SKILL.md + frontmatter，并支持外部技能库

- **日期**：2026-08-17
- **状态**：已采纳

## 背景

本仓的技能一直是「SKILL.md（纯正文）+ 旁边一个 `skill.json`（id/triggers/tools）」，加载器
只扫 `skill.json`。

而**业界通行的写法是 Markdown + YAML frontmatter**（Anthropic Agent Skills / Claude Code
就是它）：元数据和正文在同一个文件里，附属的脚本、参考文档放在同目录按需读取。JSON 在这套
体系里是**工具**的格式（function calling 的参数 schema、MCP 的 tool definition，那些要被
程序校验），不是技能的格式 —— 技能是写给模型读的散文。

代价是实打实的：IvyeaOps 的 Skill 中心有 98 个技能，全是 frontmatter 格式，本仓**一个都
加载不进来**。上游只能把技能复制一份、转换成 `skill.json`、再往正文里塞一行目录说明，才能
让它们被匹配到。复制就有一整套麻烦：防误删手工技能、防顶掉内置技能、每次改完要重新同步、
而且永远慢半拍。

同时暴露出一个更基础的缺陷：`_terms()` 用 `[\w一-鿿+.-]+` 取词，**中文不分词** ——
「做个市场调研看看这个类目」是**一个**词，不可能出现在任何技能文本里。中文提问的匹配分
恒为 0。这个缺陷此前被上游的"给每个技能手工配一批中文短触发词"掩盖着。

## 决策

1. 加载器**两种格式都认**：`skill.json` 在就按它（老技能一个不动），不在就读 SKILL.md 的
   frontmatter。
2. 支持**外部技能库根目录**（`IVYEA_SKILL_ROOTS` / settings 的 `skill_roots`），
   技能**原地加载，不复制**。
3. 中文查询按 **2-gram** 切词；相应地把打分改成"标识/标题/描述加权 + 正文命中封顶"。
4. 带附属文件的技能，在渲染和自动匹配的上下文里**告诉模型目录的绝对路径**。

## 理由

**为什么不让上游继续转换**：转换层要维护复制、清理、防覆盖、防误删四件事，还引入"改完
没同步"的时间差。而两边格式本来就该是同一种 —— 收敛格式是治本，转换是治标。

**为什么 2-gram 而不是引入分词器**：装一个中文分词器（jieba 之类）是几 MB 的词典加一个
新依赖，而这里要解决的只是"让子串能对上"。2-gram 对这个用途足够：「市场调研」切出的
"市场""调研"正是技能描述里真实出现的词。噪音（"帮我""这个"）几乎不出现在技能文本里。

**为什么必须同时改打分**：切了 2-gram，长正文的技能会靠噪音词堆分 —— 实测一个几千字的
审计技能能在"写一版主图创意"这种毫不相干的查询上排第一。分词和打分是同一件事的两面，
只改一半会让匹配比改之前更差。

**为什么外部库不许覆盖内置技能**：上游挂上来的目录里随手建一个同名技能就把内置技能顶掉，
表现为"内置技能突然换了套说法"，两边看起来都正常，极难排查。个人技能
（`~/.ivyea/skills`）保持原有的覆盖语义 —— 那是本机作者的明确意图。

**为什么加 PyYAML**：frontmatter 里的 description 有冒号、中文标点和引号，手写解析器在这种
输入上错得很安静。PyYAML 是最普遍的 Python 依赖之一，成本可接受。加载器对它缺失做了容错
（跳过 frontmatter 技能而不是整个崩掉），老环境升级上来不会炸。

## 后果

- IvyeaOps 侧那 240 行的同步器整个删掉了，改成往 settings 里写一个目录。Skill 中心里改完
  **立即生效**（实测：新建技能后 agent 当场就能匹配到）。
- 匹配质量的取舍要说清楚：**触发词写成长句会稀释匹配**。`amazon-market-research` 那个技能
  把 triggers 写成「调研报告、选品调研、市场分析、竞品分析、类目分析」这样的整串，还混进了
  "帮我分析这个类目"这种口语。加载时按分隔符拆开缓解了一部分，但根本解法是数据 ——
  触发词就该是短词。
- 打分的常数（正文封顶 2、描述封顶 3、加权 3、触发词加分封顶 9）是在真实技能库上量出来的，
  不是拍的；改动它们要重新在真实库上验证，别只跑单测。
- 未做：`skill.json` 没有废弃，内置技能仍在用。要不要统一到 frontmatter 是下一个决定。
