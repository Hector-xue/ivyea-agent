# ADR-0040 · 判"用户想干什么"只看意图正文，URL/路径/代码是素材不是意图

- **日期**：2026-09-10
- **状态**：已采纳
- **依据**：2026-09-10 会话；用户实测的两段对话（14 分 32 秒 / 10 分 8 秒）

## 背景

用户说：

> 把 `https://github.com/xdash/FDE-the-Guidance-Book-of-Forward-Deployed-Engineer.git`
> 这里面的 .md 文件给我下载下来

这个任务跑了 **14 分 32 秒、约 55 次工具调用**，其中真正干活的只有 7 次左右。换个说法
重问一次，又跑了 10 分 8 秒。agent 自己复盘时把账算在"我把简单任务当项目管了"，
但那是结果不是原因 —— **它是被框架逼的**。

链条是这样的：

1. `requires_progress_reporting()` 对**原始查询文本**做子串匹配。仓库名
   `Forward-Deployed-Engineer` 里的 **`deploy`** 命中了动作词表。
2. 同一个 URL 让整句长度到 95 字，越过了 `len >= 60` 这条线。
3. 判据 `actions >= 1 and len(clean) >= 60` 成立 → `progress_required = True`。
4. 于是每一个"实质工具"调用之前都要过三道门禁：有没有 todos → 有没有
   `progress_update(start)` → 有没有 `phase_start`。三道是**三个独立的 return**，
   模型每补一步就被下一道拦一次。
5. 更糟的是 `read_file` / `list_dir` / `grep` 也在拦截范围内 —— 想先看一眼再定计划都
   不行，计划只能靠猜着写。

一句"下载几个 md 文件"，因为仓库名里恰好有 "Deployed" 这个词，被判成了需要全套多阶段
汇报的复杂工程。

## 决策

1. **意图判据只看剥过的正文**（`task_scope.intent_text`）：URL、代码块/行内代码、
   文件路径一律剔除后再做子串匹配和长度计算。项目名匹配仍然用原文 —— 路径和仓库名
   正是它要找的东西。
2. **长度阈值 60 → 120 字**。长度是三条判据里最弱的一条，误判代价却很实在。
3. **只读工具不受汇报门禁管**。拦的是真会改动状态、花时间的那些。
4. **三道门禁合并成一条消息**，一次把缺的几步说完（同一条 assistant 消息里的多个
   tool_calls 是顺序执行的，模型可以一轮补完），并明确给出退路："若这其实是个一步
   就能做完的小任务，开一条 Todo 即可，别拆成多阶段"。

## 理由

**为什么根因在"匹配对象"而不在"词表"。** 往词表里删词（比如去掉 `deploy`）只能挡住
这一个例子：下次是个叫 `fix-cli` 的仓库、或者路径里有 `test/`，一样会中。问题出在
**拿素材当意图**——用户贴的 URL、路径、报错、代码，都是他给的**材料**，不是他对要做
什么的表述。这个判据以后还会被复用到别处，收口在输入端才是对的。

**为什么长度这条不能删只能提高。** 它确实抓得住"一段有前因后果的长需求"。但 60 字在
中文里太短了 —— 一句稍微交代清楚点的话就够。配合剥掉 URL，120 字才对应真正的长需求。

**为什么只读工具要放行。** 强制"先写计划再看代码"的结果是计划靠猜。先看一眼再定计划
本来就是更好的做法，而只读工具既不改状态也不贵。

**否掉的做法：让模型自己判断该不该走重流程。** 系统提示里本来就写着"单步、明确的小
任务别过度汇报"，而门禁是硬拦 —— 提示和执行互相打架时，赢的永远是硬拦。要么两边一起
放松，要么就别在提示里写一句做不到的话。

## 后果

- **子串匹配这件事本身要警惕**。这个仓库里还有若干处对用户文本做 `in` 判断的地方
  （`_BEHAVIOR_HINTS` / `_ENGINEERING_HINTS` / `_EXECUTION_EXPECTED_HINTS` 等），
  这次一并改成看 `intent_text`。以后新增判据，默认就该用它。
- 判据收窄之后，**真正的多步任务仍然要能触发**。测试里钉了四条正例
  （多阶段陈述、"全面检查"、"修复并验证"、含顺序词的长需求），改判据时不能只看负例。
- 门禁合并后，被拦一次仍然要花一轮。彻底消除需要让模型在**第一条消息**里就把汇报闭环
  开好 —— 那是提示词的事，这次没做。
