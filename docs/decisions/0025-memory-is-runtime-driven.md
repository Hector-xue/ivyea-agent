# ADR-0025：记忆由运行时驱动，而不是等模型想起来去查

- 日期：2026-08-27
- 状态：已采纳

## 背景

记忆这套东西的**算法层**从 2026-08-15 起就是完整的：三层记忆（核心/分类/情景）、
语义与词法双路 RRF 召回、遗忘打分、时效双时间轴、溯源置信、待定区、评测框架，
2500 多行，对标 Mem0/MemGPT 不落下风（见 [ADR-0006](./0006-memory-and-retrieval.md)）。

但用户的体感是"记性不如 ChatGPT 网页版和 hermes"。查下来根因有两条，都不在算法层：

**一、serve 这条路上一行记忆代码都没有。** `service._chat_messages()` 拼 system prompt
时注入了审批档位、板块工具桥、Skill，唯独没有核心记忆和记忆索引 —— 而 CLI 的
`_sys_msg()` 是有的。用户日常主力入口（IvyeaOps 工作台、飞书、任务台）全走 serve，
于是模型根本不知道记忆库里有什么，也就不会去 `memory_search`。同时这些对话也不进
情景记忆、不触发反思：**越在网页端用，记忆越不长**。

**二、召回是 model-driven 的。** 模型得自己想起来去调 `memory_search`。
"忘了查"因此成了最常见的失败模式。而 hermes 的做法是运行时在每轮开口前先查一遍
（`agent/turn_context.py` 的 `prefetch_all`），ChatGPT 网页版同理（saved memories 常驻
+ 每轮检索历史对话）—— **模型压根没有"忘了查"的机会**。

## 决策

1. **serve 补齐注入**：核心记忆 + 分类记忆索引层进 system prompt，位置排在审批档位/
   板块桥/Skill **之前**（那些是祈使句，谁离结尾近谁约束力强）；对话入情景记忆；
   轮末触发反思。
2. **召回改成运行时驱动**：每轮开口前自动检索一次，结果以**后缀**拼在用户这句话尾巴上，
   和 `[Ivyea 本地知识检索]` 并排。
3. **反思改成事件驱动 + 后台线程**：不再卡在 CLI 退出那一下（serve 根本没有"退出"），
   门槛随之从 12 条经历降到 8 条。
4. 配套的几道闸：trivial 门、跨轮去重、词法地板、写入熔断、核心记忆漂移保护、
   情景记忆保留策略。

## 理由

- **为什么注入形态选"后缀"而不是独立消息**：仓库里本来就有两套注入约定 ——
  门禁类走独立 user 消息 + `transcript.gate_text` + `_USER_MARKERS`，上下文类走
  "拼在真实 user 消息尾巴上 + 展示端按后缀截断"。记忆召回和知识检索是同一类东西，
  跟着后者走，就自动继承了已经在生产上验证很久的那条管道，不必新造一套机制。
  代价是**四份剥离清单必须同步**（`task_scope._INJECTED_MARKERS`、ops 前端
  `stripInjected.ts`、ops 后端 `clean_preview`），漏一份用户就会在自己的绿气泡里
  看到一大段记忆。

- **为什么不抄 hermes 的 `api_content` sidecar**：hermes 把召回只注入"发给模型的副本"、
  不落盘，于是下一轮 replay 出来的前缀和上一轮发出去的不一致，把后面整段重新 prefill；
  它为此又加了个 sidecar 存"真正发出去的字节"。ivyea 的既有约定是**照塞照落盘、
  出口才摘**，本来就满足"replay 与发送一致"，再引入第二套机制只是多一个漂移点。

- **为什么自动召回要额外加"词法重合 > 0"这道地板**：语义那一路是刻意没有相似度地板的
  （实测 bge 正确匹配只有 0.41~0.55、错配 0.29~0.55，按直觉设阈值会把正确结果静默杀光，
  见 ADR-0006）。后果是它对**任何**查询都能排出"最相似的四条"。对 `recall` 工具没问题
  ——人主动要求回忆，给个最佳猜测是对的；但自动召回是每轮无条件注入，没有地板就等于
  每轮往上下文里塞四条随机记忆，把一句本该一行带过的回答带偏。实测拿
  "量子色动力学的渐近自由"去查，整个记忆库都被召回了。
  代价是纯语义命中（口语化提问）进不了自动召回，那类查询留给 `memory_search` 工具。

- **为什么去重只做减法、不补位**：第一版为了"填满配额"把候选窗口扩到 `limit + 已注入数`，
  实测第二轮问同一件事时前几条全被去重挡掉，于是拿勉强过了地板的边缘条目补位 ——
  表现为"聊得越久，注进去的记忆越离题"。宁可这一轮什么都不注，模型手里还有索引层。

- **为什么自动化轮次不注入也不记**：`chat_run` 不只服务人机对话，定时巡检、任务台续跑、
  ad_audit 走的是同一条路。给它们注入用户画像会让结构化输出被偏好带偏（IvyeaOps 那边
  有消费方在解析），而把巡检记录喂给反思会把机器的例行输出概括成"用户的习惯"。
  opt-out 复用现成的 `inject_retrieval`（任务路径本来就传 False）+ `task_id`，零新增机制。

- **为什么反思不许改用户亲口定的规矩**：实测翻过车 —— 用户的规矩是"未经批准绝不发版"，
  反思从几次行为里总结出"他习惯开发完就发版"。统计上成立、证据门槛拦不住。
  现在 `source != "reflection"` 的 user/feedback 记忆，反思只能提改动建议进待定区。

- **为什么反思锁和记忆写锁分开**：反思里包着一次最长 120 秒的模型调用。占写锁的话，
  这两分钟内所有 `memory_write` / `core_memory_edit` 都要排队，用户会看到
  "说了记住、半天没反应"。

## 代价

- **每轮多一次检索**，system prompt 也变长。索引层限 3500 字、核心记忆限 6000 字、
  召回块限 1200 字，都有硬上限；`index_digest` 加了缓存（签名=条数+mtime+字节+当天），
  实测 5.42ms → 0.26ms。
- **反思更勤 = 模型调用更多**。可以给它单独配便宜档（`memory_reflect_model`），
  或整个关掉（`memory_auto_reflect=false`）。
- **情景记忆开始快速增长**：serve 每轮 +2 行。为此加了保留策略（默认 180 天，
  只收 `[对话:*]`），这是整套方案里**唯一不可逆**的一步，首次执行前会备份 `memory.db`。
- **作用域（按项目隔离）默认关**：现存记忆的 scope 写法是 `project:ivyea-note` 这种，
  而 workspace 推导出来的是目录名，两者对不上，开了会让"以前想得起来的现在想不起来"。
  等管理界面（能看见并改 scope）做出来再开。
