# ADR-0033：中文查询要真的能检索，评测要测回答而不是召回

- 日期：2026-08-30
- 状态：已采纳

## 背景

用户反馈"亚马逊专业能力弱"。查下来症结不是知识卡不够，而是**评测测的东西和目标能力没有相关性**：
`knowledge_quality` 41/41 满分、`evals` 31/31 全绿，但真去问运营的原话——

- `广告花了钱不出单` → 检索**零命中**
- `链接突然没曝光了` → 门控判 `should_retrieve=False`，检索根本没被触发

顺着注入路径（`evidence_context`，`service.py` 和 `cli.py` 都走它）往下挖，是叠了几层缺陷：

1. `re.findall(r"[\w一-鿿+.-]+")` 对中文**等于没分词**，整句被吃成一个 token，
   那个"词"不在任何卡片里，词法必然零命中；只有恰好撞上 ALIASES 子串的查询才有救。
2. 打分是裸词频，**没有文档长度归一化**。用户知识卡里混着整篇转载文章（实测最大 857KB，
   中位数才 683B），长文档把官方卡全挤出候选池。
3. 站点加分只硬编码了日本站和英国/欧洲站，加拿大、墨西哥、新加坡、印度、澳洲、中东站
   全靠词法碰运气。
4. 摘录取的是卡片开头，而每张卡开头都是 `Source type / Source URL / Retrieved at` 元数据——
   这些字段在引证行里已经原样给过模型一遍，等于拿注入预算换重复信息。
5. 证据文本"全部拼好、超了砍尾巴"，于是**召回更多反而看到更少**：同一个问题 `limit=5`
   把总长顶过 `max_chars`，一刀切掉尾部，连引证键一起切没，效果比 `limit=4` 还差。
6. 内置知识卡正文是**英文**的（"曝光"在卡里写作 impressions），中文口语在词法层的真正桥梁
   是那张 92 条的 ALIASES 表，不是分词。

## 决定

**检索侧**：中文 n-gram 分词 + BM25（含长度归一化）+ 标准 IDF；站点加分改成由卡片
`marketplaces` 字段驱动的通用匹配；摘录跳过元数据头并取命中最密集的窗口；证据预算按证据
优先级**加权分配**而不是拼完砍尾；域门控补运营口语词；ALIASES 补一批中→英映射。
另加一路向量召回，与词法**并列**做 RRF 融合。

**评测侧**：案例集从"召回对不对"扩展到"证据够不够回答"——加 `golden_points`（黄金要点覆盖）、
`forbidden`（禁止说法）、`expect_guard`（幻觉陷阱题必须带上护栏卡）、`expect_gap`。
另加 `known_gap`(xfail) 机制，和一层真跑主脑生成回答、复用 `critique.py` 分域 rubric 判分的
`answer_evals`（独立命令 `ivyea answer-eval`，不进 CI）。

## 理由

**向量为什么是"并列融合"而不是"给词法候选重排"**：重排方案在词法零命中时**没有候选可排**，
而中文口语问法恰恰就是词法零命中那一类——那正是最需要向量的场景。这个坑在记忆检索上踩过
一次（见 [ADR-0006](./0006-memory-and-retrieval.md)），不重复踩。

**向量路为什么是有条件跑**：它本机实测约 480ms（2287 个分块逐个解码算余弦），而注入是每条
消息都走的热路径。它的职责是补召回，所以只在词法拿不到足够权威卡时才付这个代价；索引缺失
时直接放弃、**绝不触发同步重建**（`retrieval_index.search` 在空索引上会当场重建全部分块）。
稠密向量上知识卡是后续工作，阻塞项写在 `retrieval_index.py` 模块头。

**门控补词为什么要挑**：这个 agent 同时是编码助手。"链接"是 link/编译链接、"评论"是 code
review、"索引"是数据库索引——收进域词表会把亚马逊证据注进编码对话。只收亚马逊运营专有的说法。

**`known_gap` 为什么必须留在案例集里**：把红的案例删掉换来的绿色是假的。已确认修不了的知识
缺口不计门禁，但要一直显示，否则缺口就从视野里消失了。

**答案级判分为什么不进 CI**：慢（每案例两次模型调用，实测分钟级）、要花钱、分数有波动。
放进门禁会让门禁变得不可信，也会让人开始忽略它。

## 后果

- 门禁：`knowledge_quality` 49/49（+3 known_gap）、`evals` 31/31、全量 2101 passed。
- 注入延迟 350–410ms → 31–96ms（向量路改成有条件跑之后，比改动前还快）。
- 判分层首跑就抓到召回评测抓不到的东西：`ads.attribution` 召回排名第 1，回答却被 rubric
  判"建议修正"。
- 暴露出三个**真实内容缺口**（已标 known_gap）：知识库没有 buy box/跟卖 卡、没有 review/差评
  卡；问"卖家等级 S3 认证"这类编造机制时召不回护栏卡。
- 遗留一个**改动前就存在**的门控误报：`编译链接报错 undefined symbol` 会触发亚马逊检索
  （因为"报错"在域词表里）。没顺手改是怕碰坏 90220 那批错误码案例，留待单独一轮。
- 教训：**评测满分不等于能力达标**。这套评测存在了很久且一直全绿，而它测的召回和用户感受到
  的专业能力之间没有相关性。新增能力时，先问"这个评测红了能说明什么"。
