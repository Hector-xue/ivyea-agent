# ADR-0031：一轮跑着的时候，人还能说话（也能叫停）

- 日期：2026-08-28
- 状态：已采纳

## 背景

一轮 agentic 任务动辄几十分钟。这几十分钟里，人是**闭麦**的：

- 想补一句"顺便把 X 也改了"，只能等它跑完，或者掐掉重说一遍（前面几十分钟连同
  上下文一起作废）；
- 模型自己撞上岔路时也没人可问。系统提示里那条"澄清"纪律在非交互的一轮里只能
  表现为**把问题写进回答然后结束这一轮** —— 用户离开五分钟回来，看到的是一个
  问句，什么都没做。

两件事的根子是同一个：**一轮开跑之后，输入通道就关了**。轮次只在开头读一次
用户输入，此后到收尾之前，人和它之间没有任何一条路。

## 决策

给正在跑的轮次开三条**反向**通道（补话、问选择、叫停），都收敛到"一定有结果"，
绝不新增可能挂死的地方。

### 一、追加指令：收件箱 + 步边界注入

`turn_inbox`（进程内、按 session 分格）收投递，`agent_loop.run_turn_stream` 在
**两个工具步之间**排空它，把每条作为一条真实的 user 消息（`[用户追加指令] …`）
追加进当前上下文。模型下一步就看得见。

三个刻意的选择：

- **只在步边界插**。assistant(tool_calls) 与它的 tool 结果之间插一条 user 消息，
  provider 会直接拒掉整轮 —— 这不是风格问题，是协议问题。
- **模型正要收工时再看一眼收件箱**。用户最常补话的时刻恰恰是"看着它快跑完了"
  那一下；只在循环顶部排空的话，那句话一律要等下一轮。
- **注入后复位 loop_guard**。局面变了，之前攒的"卡住"判定不该压在新指令上，
  否则用户刚说完话就被告知"你卡住了，停下来说说卡在哪"。

追加指令是**用户真说过的话**，所以它不进 `transcript._USER_MARKERS`：历史里要留着，
并且自成一轮（`turn_slices` 按 user 消息切）。摘掉它等于让"我中途说过什么"从记录里
消失。

没被消费的条目不许无声消失：轮次收尾时端给调用方（`final.injected_pending`），
由它当成下一轮发出去。宁可晚一轮，不能吞掉一句话。

### 二、选项卡：`ask_user_question` + 五分钟推荐兜底

新工具把岔路做成 2-4 个选项弹给用户，每个选项写清楚"选它会发生什么"，其中一个
标 `recommended`。通道有三种实现（serve 的远程卡片 / 终端菜单 / 没有通道），
但**语义只有一条**：

> 五分钟没人选，就按标了推荐的那一项继续，并且把这件事记账。

这条是整个设计的重心。"问了就等着"会让无人值守的任务全部卡死；"不问直接猜"
则是现在的毛病。给一个有明确默认值、有截止时间的问题，两边都成立：人在的时候
一点即走，人不在的时候任务照样跑完，而且事后说得清是谁定的。

**记账必须是确定性的**（同 `memory_recall` 的成例）：自动定的项进
`ctx.auto_decisions`，随 `final` 事件端给界面，由界面自己画说明块。同时也在工具
返回值里要求模型在总结里复述 —— 两条腿走路，因为模型经常不提。

护栏：每轮最多问 3 次；不进 `READONLY_TOOLS`/`PARALLEL_SAFE`（子 agent 没有界面，
不该替用户做选择题）；闲聊路线本来就不挂工具，自然不会问。

#### 补记（2026-09-02）：给的选项永远列不全

上面这套只留了"在 2-4 个选项里挑一个"这一条路。实际用起来缺两条出路，三个界面
（工作台的卡、/agents 那张面板、终端菜单）里只有 /agents 那张有：

* **自己写一个答案** —— 模型列的选项不可能覆盖所有做法。没有这条，用户想说第五种
  就只能干等超时、或者另起一句话说，而那句话已经不在这张卡的上下文里了。
  实现上不需要任何新协议：`_clean_answers` 本来就"值原样保留"，自由文本和选项
  标签走的是同一条路。
* **跳过这题** —— 明确把这一项交回给模型。实现是提交时**不带**这一问，后端照旧
  按推荐项补齐并记进 `auto_filled`。所以跳过不是把问题丢掉，是留了痕的放权。

补的时候发现一处会对用户撒谎的地方：`resolve` 原来只看"答案是不是空的"来判超时，
于是用户明明点了跳过，收尾却说"你在 5 分钟内没有选择"。现在按**通道回的是不是
None** 来分：`None` = 真没人答（超时/页面关了/非 tty），空 dict = 人在场、他跳过了。
两者答案完全一样（都按推荐项），但 `reason` 分别是 `timeout` 和 `skipped`，工具
返回值和界面说明块都按它分开措辞。

终端那两项固定挂在菜单末尾，"跳过"排最后 —— 降级菜单（非 tty 的编号输入）约定空
输入落到最后一项，而"不选＝跳过＝按推荐继续"正是想要的兜底。全屏 TUI 里的自由
作答不另开输入框：底下那个一直都在，工具线程通过 `tui.set_active_prompt` marshal
回主 app 收一行（和审批菜单同一个套路）。这里有个必须钉住的顺序 —— 回车分支里
"自由作答"要排在"运行中排队"**前面**：自由作答就发生在工具跑着的时候，顺序反了
用户的答案会被当成追加指令排进队列，选项卡永远等不到。

### 三、停止要真的停

同一个根子的第三件事：那颗「停止」从来没有停过任何东西 —— 调用方只是断开自己
那条事件流，轮次在这边照跑照烧 token（用户原话："有的任务不想做了却无法终止，
难道要一直烧 token 吗"）。

`POST /v1/chat/cancel` 置一个**服务端**的中止标志（按停止的那个页面可能刚好断线，
甚至是另一台机器上的另一个标签页 —— "别再烧了"和哪条连接还活着没有关系），
轮次线程在 `cancel_check` 的三个既有落点读它：模型流的每个事件、每个工具步边界、
每一步循环顶部。所以它停在几百毫秒之内，而不是等这一轮跑完。

三个刻意的边界：

- **不杀线程**。停止不该是"把现场砸烂"：正在写的文件、正在收尾的落盘都得让它走完。
  代价是**正在执行中的那一个工具调用不会被打断**，最坏要等它结束。
- **已经跑出来的东西照常落盘**。半截的正文和执行过程也是真发生过的，不能因为
  用户改了主意就抹掉。
- **发 `cancelled` 而不是 `error`**。界面会把 error 画成红色的失败 —— 而这不是失败。

### 四、`-p` 也要有这三条通道（v1.16.1 补齐）

上面三条通道都长在 serve（常驻 HTTP）上。但**消费方不止 serve**：IvyeaOps 的
`/agents` 聊天走的是 `ivyea chat -p` 子进程，隔着进程边界够不着 serve 进程里的那些
注册表。于是同样三件事在那边一件都做不成，而且"停止"只能 SIGTERM —— `_persist()`
来不及跑，整轮产出蒸发。

所以 `-p` 自己开一条：`--input-format stream-json`，stdin 逐行收控制消息
（`user_input` / `control_response` / `interrupt`），stdout 混发 `control_request`。
形状照抄 Claude Code 的 stdio control protocol —— IvyeaOps 的 claude_driver 已经在说
这套话，消费方少学一套。

读 stdin 的是**守护线程**，轮次线程只在自己的安全点（步边界、模型流的每个事件）
来取：什么时候有人说话完全取决于人，不能让轮次阻塞在读上。

### 五、时间是服务端的事实

顺带把"这一轮什么时候开始、什么时候结束、跑了多久"落盘（`turn_times`，与 `steps`
一样**平行于 messages**存 —— message dict 会原样回灌给 provider，多一个自定义键
就有被拒的风险）。

客户端自己掐的表在断链、换标签页、换台机器之后一个数都不剩，而一轮跑完前端还会
重新拉一次存档、把内存里的数冲掉。轮号口径与 `transcript.turn_slices` 同源（都数
"第几条真实用户消息"），所以时间戳不会错位 —— 错位的时间戳比没有更糟，它看着是真的。

## 结果

- CLI：`ivyea chat -p --input-format stream-json`（v1.16.1）。
- serve：`POST /v1/chat/inject`、`POST /v1/chat/question`、`POST /v1/chat/cancel`、
  `GET /v1/chat/live-sessions` 四个新端点；`final` 增加 `auto_decisions` / `injected` / `injected_pending` /
  `started_ms` / `ended_ms` / `ms`；SSE 增加 `injected` / `question_request` /
  `question_timeout`。
- 老调用方零影响：`inject_check` / `on_inject` / `ask_fn` 不给就是原来的行为，
  一个字节都不变。
- `GET /v1/chat/live-sessions` 读内存里的活轮登记，不扫会话文件 —— 它会被界面
  按秒问。
