# ADR-0022：促销规则只报不改，且必须先报"数据还能不能信"

- 日期：2026-08-23
- 状态：已采纳

## 背景

巡检原本盯的是库存、广告、listing、跟卖。运营每天还要盯一件事：**报了的活动什么
时候结束、哪个 ASIN 的券快到期**。错过截止时间的代价是实打实的（活动停了没人知道，
或者券的预算悄悄花完、商品页上那行 coupon 不见了）。

数据通道是现成的：领星 OpenAPI 有四条促销活动列表路由 + 一条按 ASIN 的路由，
本机 2026-08-23 实签调用全部 `code=0`。

## 决策

新增 `promotion.active` 指标与 4 条 L1 规则：活动即将结束（24h / 6h 两档）、
活动即将开始、优惠券预算见底（80% / 95%）、**促销数据停更**。

三条与既有规则不同的取舍：

### 一、这四条一律不带 `intent`（可执行动作）

其余规则能给"降预算"这种一键按钮，是因为背后真有写接口。促销不一样：**延长活动、
加券预算、改折扣，在领星 OpenAPI 和亚马逊官方 API 上都没有写接口** —— 促销本来
就只能在卖家后台操作。

给一个点了没用的按钮，比不给更糟：它会让人以为点了就处理完了。这几条的价值是
"别错过截止时间"，人收到提醒去后台处理即可。

### 二、必须有一条规则报"数据本身停更了"

领星的促销数据**不是 API 直连亚马逊拿的，是「LINGXING助手」浏览器插件抓的**
（官方要求助手保持登录在线）。插件掉线时，接口**照样返回 200 和一批旧数据** ——
倒计时会安安静静地停在过期的值上。

这比"没有数据"危险得多：没有数据时人知道自己不知道；停更的数据会让人以为自己
知道。所以 `promotion.sync_stale` 报的不是某个活动出了问题，而是**上面三条规则的
结论全都不可信**。每行数据都带 `sync_age_hours` 就是为这条。

接上亚马逊官方通道（SP-API 的 `GET_COUPON_PERFORMANCE_REPORT` /
`GET_PROMOTION_PERFORMANCE_REPORT`）就没有这个问题 —— 那是 P7 的事，指标层已按
provider 抽象留好位置（ADR-8）。

### 三、每档只报一次，不是每小时报一次

L1 每小时跑一轮。一个活动从报名到结束会经过几十轮巡检；每轮都提醒的机器人，
三天就会被静音，那时候真到期也没人看。所以只在跨过 24 小时和 6 小时这两个刻度的
那一小段里报（窗口取 1 小时：比这窄，一次巡检失败就整档漏掉；比这宽，会连报两轮）。

## 顺带修掉的一个坑

促销接口的金额字段带货币符号：`"JP¥10,084.0"`。通用的数值转换只剥逗号和百分号，
遇到货币前缀直接落回默认值 —— 预算永远是空，"预算见底"这条规则**永远不会触发**。
这类"规则写了但永远不响"的 bug 不会有人报，只能靠测试逮住（本次正是被测试逮住的）。

## 后果

- 本机账号当前没有任何促销数据（四个接口 code=0、total=0，历史窗口也空），所以这批
  规则**只做了契约级 + fixtures 验收**，真数据验收要等一个在跑活动的账号。
- 站点时区表进了 `stores.py`。领星给的是站点当地时间的裸字符串，按服务器时区算，
  UK 的活动会差 7~8 小时 —— 正好是"以为还有一天、其实已经结束"这种最坏的错法。
