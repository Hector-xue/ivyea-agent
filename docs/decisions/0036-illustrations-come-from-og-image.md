# ADR-0036：回答里的配图去网页上找，不去模型里画

- 日期：2026-09-02
- 状态：已采纳

## 背景

用户拿 ChatGPT 的回答做对比：问"你了解过 51WORLD 这家公司吗"，它在正文旁边贴了三张图 ——
公司展台照、官网首图、产品页截图。同样的问题在 IvyeaOps 里只有纯文字。

这个差距不是模型能力差距。看清楚 ChatGPT 那三张图的来源就明白了：它们**不是画出来的**，
是它搜到的那几个网页各自的分享预览图。搜索管线顺手就带回来了。

我们当时手上有的两个工具都对不上这个需求：

- `image_generate` 是**画**图。画一张"51WORLD 的展台"既慢（十几秒起）又是假的 —— 用户要看的
  是这家公司真实长什么样，编一张出来还不如不给。
- `show_image` 只能展示**本地已有**的文件。回答一家没接触过的公司时，本地什么都没有。

`web_search` 倒是每次都在跑，但它的正则只抠 `<a href>` 和标题，页面里的图片信息全丢了。

## 决定

新增只读工具 `web_images`：搜一批相关网页 → 并发抓每个页面的 `og:image` / `twitter:image`
→ 校验后返回可直接写进正文的 markdown。系统提示词里给出使用边界：具体的公司、产品、地点、
实物、界面、人物才配图；抽象概念、纯数字结论、代码问题不配。

选 og:image 而不是接图片搜索 API，理由是它**零 key、零成本**且质量有下限：一个网页声明的
分享预览图就是这个页面的作者挑出来代表这个页面的图，天然切题。付费图片搜索（Brave / SerpAPI）
召回更全，但要为一个锦上添花的功能常年付月费，不划算。

## 三个非显然的坑

**一、判"这是不是一张能用的图"要量像素，不能量字节。** 第一版按 content-length 过滤（<6KB
判为图标），实测站点 logo 有 40KB 的、正经配图有 12KB 的，两边都判错。改成用 Pillow 的增量
Parser 边下边解析文件头，拿到真实宽高再判（≥320×200、长宽比 0.25~4）—— 只需读开头几 KB，
不用整张下载。

**二、慢站必须有总预算，否则配图会拖垮整轮回答。** 第一版给每个请求 6 秒超时就以为够了，实测
一个 query 跑了 **49 秒**：httpx 的 timeout 是分阶段的，连接、读取各算各的，几个慢站串起来就
超了。现在分阶段超时收紧到 connect 3s / read 4s，外面再套一个 20 秒总预算 —— 到点就用手上已有
的图交差，一张都没有就明说配不出图。配图是锦上添花，绝不该让用户为它多等。

**三、（消费方侧）第三方图床看见 Referer 会 403。** 实测百度百科图床：不带 Referer 返回 200，
带 `Referer: https://ivyea.com/` 直接 403 text/html。IvyeaOps 那边渲染正文图和灯箱原图时都必须
`referrerPolicy="no-referrer"`，否则配图链路全通了、页面上却是一片裂图。

## 影响

- `web_images` 是只读工具，自动放行、可并行，只读子 agent 也给（调研角色经常要配图）。
- 配不出图时返回明确的"配不出图"而不是空串 —— 模型不能把沉默当成拿到了图。
- 消费方约定：正文里出现的 `![说明](地址)` 可能指向第三方图床，渲染方要 `no-referrer`。
