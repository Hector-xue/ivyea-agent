# ADR-0032：会话附件不是知识

- 状态：已采纳
- 日期：2026-08-30

## 背景

IvyeaOps 任务台的「+」按钮，此前对非图片文件只有一条路：调 `/v1/knowledge/upload`
进知识库、建索引、永久留档，然后在输入框里代写一句「已把「X」加进知识库，可以直接问
它的内容」。

用户的原话是：

> 有些文件只是会话的时候用，并不需要纳入知识库啊。

这条路没有出口 —— 想「就这次问问」也得先污染知识库，之后还得自己去清。而知识库是长期
资产：它进检索、进引证、进覆盖率统计，塞一份临时报价单进去，之后每一次检索都得从它旁边
绕过去。

## 决定

**加一条只抽正文、什么都不留的路，并把它设成默认。**

1. 新增 `POST /v1/files/extract`：复用 `knowledge.extract_document_text`
   抽正文，**不写知识库、不建索引、不留档**。
2. `_attachments_note` 按 `kind` 把附件分流成两段注入，文档走 `[用户附件 —— 文档正文]`。
3. 想长期留着仍然走 `/v1/knowledge/upload` —— 在界面上是附件胶囊上一个**显式按钮**。

### 为什么抽取留在 agent 这边

ops 是 HTTP 客户端，没法 import 这边的函数；而它自己只装了 pypdf / openpyxl，
**没有 python-docx**，自己抽会漏 docx。更要紧的是：两边各写一套抽取逻辑，同一份文件
读出来的字迟早会不一样，而"知识库里的这份"和"这轮对话里的这份"内容不一致是最难查的
那类 bug。共用同一个 `extract_document_text` 就没有这个问题。

### 为什么文档要和附图分开计数、分开限长

原来的 `_ATTACHMENTS_MAX=4` / `_ATTACHMENT_TEXT_MAX=6000` 是按"视觉模型对一张图的
描述"定的 —— 一段描述几百字绰绰有余。文档不是：一份 PDF 动辄几万字，塞进 6000 的池子
里等于每次都被腰斩，而且和图片共用份数的话，贴 4 张图就能把文档整个挤掉。所以文档另立
`_DOCUMENTS_MAX` / `_DOCUMENT_TEXT_MAX`（60000）。

**没有 `kind` 的附件一律当图片。** 这个字段是随会话附件一起加的，老 ops 送上来的
attachments 只有图、且不带 kind；默认成文档会把它们的描述文字摆进错误的段落。

## 踩到的坑

**抽出来的"正文"可能根本不是文字。** `extract_document_text` 对不认识的后缀会退回
`_decode_text`，且只在结果短于 20 字时才报 `unknown_binary_or_empty_text` —— 于是一个
`.zip` 会「成功抽出」几万个控制字符、一个 warning 都不给，然后被整段注进模型上下文
（实测确认）。既烧上下文又帮不上任何忙，还可能把请求体撑坏。

所以 `files_extract` 加了一道可打印字符占比的判据（`_looks_binary`），命中就**把正文
一并清空**而不只是加个 warning —— 留着的话调用方多半会照单全收（"有 text 就是抽到了"）。

## 影响

- 任务台传文档默认**不再进知识库**。这是行为变更，但变的方向正是用户要的；想入库的路
  没有消失，只是从"默认且唯一"变成"显式且并存"。
- ops 需要 agent ≥ 有这个端点的版本；拿不到端点时必须明确告诉用户，**不能静默退回入库**
  —— 那恰恰是被抱怨的那个行为。
