# 0039：目标模式 —— 判定权归运行时，不归模型

日期：2026-09-03
状态：已采纳

## 背景

一句话交出去，希望它自己做完。实际发生的却总是这样：模型写完代码说"已完成"，
但没跑过；跑过了，没验目标场景；验了一半，剩下的只字不提。用户得自己发现、自己
回来说"还不行"，一句话的活被切成七八轮对话。

根因不是模型不够强，是**判定权在模型手里**。"这算不算做完了"由它自己回答，而
它每一次都倾向于回答"算"。这与 [ADR-0025](./0025-memory-is-runtime-driven.md)
（记忆）和 [ADR-0026](./0026-the-plan-is-runtime-state.md)（计划）踩的是同一个坑：
**指望模型自觉的东西，等于没有**。

## 决策

新增**目标模式**：开着的时候，这一轮不是一次问答，而是一个要达成的目标。

1. **立约在先**（`goal_mode.derive` → `goal_store`）。收到指令先把它拆成可验收的
   标准，每条附「怎么验」，落盘到 `~/.ivyea/goals/<session>.json`，每轮回注上下文。
   跨压缩不丢 —— 跑到第 80 步时模型早忘了最初答应过什么，而台账没忘。
2. **判定在运行时**（`agent_loop._goal_gate_feedback`）。模型想收尾时，由运行时逐条
   对照**本轮真实的工具证据**判定，没达成就把差距注回去接着干。这是第五道门禁，
   挂在自验证/汇报/引证/自查之后 —— 便宜的确定性门先把能修的修掉。
3. **拿不准按未达成**。这与自我批判门禁（[ADR-0027](./0027-thinking-critique-and-evidence.md)：
   "拿不准一律按通过"）**故意相反**。那道门误判的代价是白跑一轮、甚至把对的答案改坏；
   这道门放水则等于把整个模式关掉，而多跑一轮恰恰是用户选这个模式时愿意付的代价。

## 什么时候真的停

"达成之前不停"必须有边界，否则就是一个烧钱的死循环。四条出口，缺一不可：

| 出口 | 机制 |
|---|---|
| 用户喊停 | 已有的 cancel（终端 Ctrl-C / 任务台停止键），在模型流与工具步边界生效 |
| 目标达成 | 全部标准进终态（`met` 或 `unverifiable`），门禁放行 |
| 成本闸 | `chat_max_cost_cny`。**步数可以续，钱不能续** —— `budget.renew_steps` 只把步数加满，`cost_cny` 一路累加 |
| 无进展熔断 | 连续几次判定结果完全一致（同一份未达成集合的指纹），说明在同一处原地踏步，停下汇报 |

步数上限从来只是防跑飞的安全阀，不是常规停止点。所以目标模式用自己的预算
（`goal_max_tool_steps`，默认 600），用完还能自动续期（默认 5 次）。用户按下这个
开关的意思就是"达成之前别停"，撞 600 步就收摊等于把承诺改成了"跑 600 步就停"。

## 为什么不另起一套 orchestrator

自主循环需要的一切 —— 计划台账、todo、阶段汇报、完成前自验证、自我批判、追加指令、
真停止 —— 这个仓库已经全都有了。缺的只有一件事：**没人拦着模型说"我做完了"**。
所以目标模式是一道门禁 + 一份契约，不是第二套执行引擎。另起一套会和现有五道门禁打架，
而且从此有两个地方决定"这一轮怎么跑"。

## 代价

- **每轮多两次模型调用**：立约一次、每次收尾判定一次。都按字符估算记进本轮成本
  （运行时自己发起的调用漏在成本闸外面，那个闸就是假的）。
- **契约可能拆歪**。所以契约与用户原话冲突时以原话为准，且 system 段里明写这条；
  拆不出标准时回落到"用户原话 + 必须真实验证"两条粗标准，而不是放弃立约。
- **验收员也会挂**。没配模型 / 调用失败 / 返回读不懂时**放行并明说**"这一轮没被验过"
  —— 不能把用户永远关在一道自己都没上班的门后面。

## 真机冒烟改掉的两处（都不是单测能发现的）

第一次真跑（一个"写个 add.py 并跑通"的小目标）**没有跑到验收判定就把钱烧完了**，
第二次撞上无进展熔断。两条根因，都改了：

1. **两套仪式会互相饿死。** 起初 `_prepare_goal` 顺手把阶段汇报闭环
   （`progress_required`）也打开了 —— 结果 28 次工具调用里 19 次是记账，两次撞上
   loop_guard 的"连续 4 次全在记账"。目标模式**不再**打开它：验收清单本身就是结构，
   而且比阶段汇报更贴近"还差什么"。该不该做阶段汇报仍由 routing 按这句话的性质决定。
2. **判定的上限就是证据通道的上限。** 喂给验收员的证据原本取自
   `progress_tool_evidence`，那里每条只留结果的**第一行** —— 而 `run_command` 的第一行
   恰好是「[退出码 0]」。于是命令原文和 stdout 全被裁掉，验收员只能一遍遍判"只有声称、
   无证据"，连判三轮相同后触发熔断：模型明明跑对了，却永远过不去。现在目标模式自己记
   一份证据（`ctx.goal_evidence`：工具 + 目标 + 成功/失败 + 输出头），并在判定提示词里
   写明证据行的格式是固定的、不要索取运行时给不出的字段。
   改完第三次真跑：一次判定，3/3 全 met，收尾回答里逐条列出了证据。

## 边界

- **只读档下不生效**。计划模式里什么都写不了，目标自然达不成，开了只会让模型在门禁前
  空转。IvyeaOps 的开关因此在打开目标模式时把审批档位一并切到「完全放行」，并且**切得
  看得见**（档位芯片当场变），用户随时能改回去。
- **没有 session_id 就整个空转**（只读子 agent、裸 ToolContext 的单测），行为与没有
  这个模块时逐字相同 —— 与 `plan_store` 同一套降级契约。
