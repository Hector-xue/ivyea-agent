# ADR-0013 · 调用方给的附图内容并进 user 消息，不放 system

- **日期**：2026-08-21
- **状态**：已采纳
- **依据**：IvyeaOps 任务台会话 `20260821-171923-592-d5bc` 的真实存档；对应 IvyeaOps ADR-0020

## 背景

主脑没有视觉时，图有两条路：agent 自己的三档降级链（ADR-0007），或者调用方先把图读成
文字再带下来。IvyeaOps 任务台走的是后者 —— 它有自己配好的视觉链，Listing 和技能商店
一直在用。

那段文字此前走 `payload["system"]`。而 system 是**每轮重建**的，落盘时又被本轮这份
整个覆盖（`sessions.append_turn` 用本轮的 system 覆盖 `messages[0]`）。于是：

- 「图里是什么」只在贴图那一轮存在；
- 下一轮用户问"你是通过什么识别图片的"，模型手里一个字都没有，只能否认自己收到过图，
  还把上一轮如实的描述说成是自己编的 —— 真实投诉就是这一条；
- 会话存档里也完全看不出用户发过图。

## 决策

新增 `payload["attachments"]`（`[{kind,name,ref,by,text}]`），内容并进**这一轮的
user 消息**，前缀 `ATTACHMENT_MARKER`（`[用户附图 —— 视觉模型代读的内容]`）。
同时在这段话里写明：图是视觉模型代读的、代读的是哪个模型、**不许否认收到过图**。

## 理由

- **user 消息是唯一跟着历史走的位置**：system 每轮重建，assistant 消息不是调用方能写的，
  工具结果需要一次真实调用。只有 user 消息既进模型、又进存档、又能被展示端按标记摘掉。
- **不选让调用方把描述拼进 `message`**：`message` 还要拿去做路线判定（ADR-0010）、
  知识检索、技能匹配和会话标题 —— 几百字的图片描述会把这四件事一起带偏。
- **不选在这里直接收图**（`payload["images"]` 走 ADR-0007 的三档链）：那条链和调用方的
  视觉链配置互相独立，用户机器上很可能只配了一边。两条链要不要合并是另一个决定，
  不该混在这次修复里。带图的一轮仍按 `has_attachments` 参与路线判定，这点两条路一致。

## 后果

- 附图内容跟着历史和存档走，多轮追问不再失忆。
- 上下文里多了一段常驻文本：一张图的描述通常几百 token，四张图会明显占位；
  真嫌重时该做的是压缩描述，而不是退回"只在当轮有效"。
- 展示端要认 `[用户附图` 这个标记（IvyeaOps 的 `lib/stripInjected.ts` 与
  `console_sessions.clean_preview` 已登记）；新增展示端漏登记的表现是气泡里出现一大坨
  代读文字 —— 和 `transcript.py` 顶上那段注释说的是同一类坑。
