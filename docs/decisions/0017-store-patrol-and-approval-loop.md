# ADR-0017 · 店铺巡检分层；证据门槛由动作可逆性决定；审批状态归 agent

- **日期**：2026-08-22
- **状态**：已采纳

## 背景

需求是四件事：店铺异常主动推送、每日早报、推送里带可执行建议、**同意后直接执行**。

动手前发现三处与直觉不符：

1. `alerts.py` 检的是 **agent 自身**健康（队列积压、trace 失败、影子台账），
   不是店铺业务。业务异常检测需要新建。
2. 「建议 → 执行」的主干**已经存在**：`lingxing_optimizer.run_store()` →
   `lingxing_write.candidate_to_intent()` → `lingxing_write.execute()`，
   内建冷却期、历史否决记忆、幅度硬闸、写前快照、失败熔断、回滚。
   缺的只是把它接到飞书按钮上。
3. `schedule.run_due()` **没有任何调用方**——只有 CLI 手动触发，crontab 里也没有。
   「每日早上」这件事当时根本没有触发器。

第一版方案里还犯了一个更根本的错误：把所有检测都绑在 T+1 的报表上，然后想用
**调阈值**来解决「紧急异常不能等一两天」。用户直接否掉了 ——
调阈值救不了隔天的数据。

## 决策

### 一、巡检频率由**数据新鲜度**决定，不由重要性决定

按接口有没有时间参数分层，各配各的节奏：

| 层 | 数据 | 延迟 | 节奏 |
|---|---|---|---|
| L1 快照 | 库存、活动/关键词配置（接口无日期参数 = 当前状态） | 秒级 | 20 分钟 |
| L2 日内 | 当日累计报表多次采样做差分 | 小时级 | 1 小时 |
| L3 隔日 | 完整报表、ASIN 利润 | T+1 | 每日 |

紧急性靠**换更快的数据源**解决，不靠降低统计门槛。

### 二、证据门槛由**动作可逆性**决定

| 类别 | 例子 | 可逆性 | 门槛 |
|---|---|---|---|
| 止血型 | 降预算、降 bid、提预算 | 完全可逆，影响有界 | 低：单点异常即可 |
| 结构型 | 否词、加词 | 不可逆（否词永久掐掉一条流量入口） | 高：需统计显著性 |
| 建议型 | 补货、改价 | 无写通道 | 只告警 |

### 三、规则消费「指标」，不消费接口

`metrics.py` 定义指标与 `DataSource` 协议，数据源负责把响应**规范化**成
canonical 字段。规则读 `inventory.fba_snapshot` 而不是
`/erp/sc/routing/fba/fbaStock/fbaList` 的原始字段。

### 四、审批状态存在 agent 侧的 sqlite，不在 relay 内存里

## 理由

**为什么不是统一阈值（原方案 v1.0）**：告警回答「值不值得你现在看一眼」，
执行回答「有没有足够证据自动改钱」。这是两个问题。用一套数字管两件事，
结果是被最保守的那条规则（否词需 ≥15 点击 0 单）拖成 T+2 才报警。
按可逆性分档之后两者不再矛盾——它们判断的本就不是同一件事。

**为什么要指标层**：用户已明确后续要接亚马逊官方 API。把规则写死在领星字段上，
届时 17 条规则要全部重写。加一层之后，同一条 `ads.spend_burst` 今天走领星轮询、
明天走推送，代码零改动；每个 Finding 还能带上「来源 X · 延迟 Y」让人知道该多信任它。

**为什么审批状态不放 relay 内存**：对照组是 hermes 的
`gateway/platforms/feishu.py:1467`——它的 `_approval_state` 是内存 dict，
因为它的审批是**阻塞式**的（agent 线程卡在那等人点）。我们是**异步式**：
告警发出去，人可能两小时后才点，relay 重启不能丢。

**为什么是 sqlite 而不是方案里写的 jsonl**：「一次性消费」必须是原子的
compare-and-set。飞书重复点击与网络重投是真实场景，
`UPDATE ... WHERE state='pending'` 的 rowcount 才能保证只有一次生效，
jsonl 的读-改-写做不到。已用 8 线程并发点击验证。

**为什么执行走 `lingxing_write` 而不是 `executor`**：后者依赖 `mcp.json` 的
`writeActions` 映射到某个 MCP 服务器的写工具，而 `lingxing_write` 有它没有的
三样东西——确定性幅度硬闸、写前快照、失败熔断。

## 后果

- 七道闸串起来：发送者白名单 / 回调会话一致性 / 卡片 token 去重（relay 侧）
  → 状态机一次性消费 / 写开关 TTL / 幅度硬闸 / 快照审计回滚（agent 侧）。
- **幅度硬闸放在写开关之前**：幅度不合法直接判失败，而不是"等你开了开关再来撞一次"。
- **写开关关着时保持 `approved` 而非 `failed`**：批准意愿仍然有效，
  补开开关后可直接重试，不必重发卡片。
- 实测挡下两个会炸的坑：领星 FBA 库存接口**把 FBM 商品一并返回**（某账号 120/120
  行为 FBM，库存恒为 0），不按 channel 过滤会对每个自发货商品误报断货；
  数值字段混用 int 与字符串（`historical_days_of_supply` 是 `"0.00"`）。
- 代价：多了指标层这层间接。但用户已明确要接官方 API，不抽象就是明知要重写还硬编码。
- 遗留：L2 依赖「当日累计值随时间滚动更新」这个假设，当前账号广告已归档无法验证。
  巡检结果里会自己报出「未观察到累计值增长」，让假设自证。
