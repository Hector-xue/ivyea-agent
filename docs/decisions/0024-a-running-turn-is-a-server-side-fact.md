# ADR-0024：正在跑的那一轮是服务端的事实，不是某个页面的内存

- 日期：2026-08-27
- 状态：已采纳

## 背景

`/v1/chat/stream` 是一条一次性的管子：事件写给发起它的那个连接，写完就没了。
一轮任务的执行过程因此**只存在于那一个浏览器标签页里**。真实反馈（逐条）：

- 切到别的会话或别的板块再切回来 —— 执行过程整块消失，只剩自己发的那句话干挂着，
  "我知道后台在执行，但前端看不到进度了"；
- 刷新同理，而且要等这一轮**整个跑完**、再刷新一次，才"一下子把所有过程和结果输出出来"；
- 换台机器打开同一条会话，什么都看不到。

轮末落盘（`sessions.append_turn`）救不了这个：一轮动辄几十分钟，那期间磁盘上除了
用户那句话之外什么都没有。

同一批反馈里还有一条更要命的：**"有时候会话结束显示了完整的输出结果，但是刷新
之后输出的结果就不见了，也没有落盘到对应的会话文件里面。"** 查下来是真的 ——
落盘只写在"正常收尾"那一条路径上，模型在收尾阶段报错（额度用尽、断流）时
`except LLMError: return` 直接走人，已经流到用户眼前的整篇正文一个字都不留。

## 决策

两件事：

1. **活轮事件日志**（`ivyea_agent/live_turn.py`）：每条会话最多一份，跑的过程中
   把所有事件记一份，跑完封存 5 分钟。新增 `GET /v1/chat/sessions/{id}/live`，
   任何客户端随时接进来 —— 先回放已经发生的，再实时跟随。会话详情多回一行
   `live: {running, seq}`，前端据此决定要不要接。
2. **任何退出路径都落盘**：正常收尾、模型报错、任意异常，一律先把已经产生的
   消息和步骤写进会话；模型死在流到一半时 `messages` 里还没有那条 assistant，
   就拿活轮日志里的正文补上 —— **已经流到用户眼前的字就是事实**。

## 理由

- **为什么不是"定期把步骤落盘、前端轮询"**：那样正文仍然不实时，而且轮询粒度
  一粗，界面就成了每几秒跳一次的幻灯片。真正要的是"接进正在发生的事"。
- **为什么正文只存一份累加字符串，不逐条存 token**：一轮几万条 token 事件，逐条
  留会把内存吃干；而客户端要的从来不是第 8137 个 token，是"现在正文长什么样"。
- **那顺序怎么保住** —— 每条结构化事件记下"我被记录时正文有多长"（`tlen`），
  回放时先把正文补到 `tlen` 再发事件。于是「说一段 → 调两个工具 → 再说一段」
  的交错逐字还原。这条交错正是前端做分段汇报的凭据。
- **为什么日志不跟着连接走**：轮次本来就与连接无关（客户端断开时 serve 会
  "无声跑完"）。日志属于会话，谁都可以接、可以断，互不影响。

## 后果

- 多个客户端可以同时看同一轮（两个标签页、手机和电脑）。
- 内存有上限：4000 条事件 + 400KB 正文，超出丢最早的并在回放时**如实报**丢了多少，
  不假装完整。
- `chat_stream` 拆成一层薄壳 + `_chat_stream`，壳只负责"无论怎么结束都封存日志"
  —— 不封存的话，跟随者会一直挂着等一个永远不来的 final。
  （按名字取源码做断言的测试要跟着改指 `_chat_stream`。）
