# ADR-0037：知识型提问单开一条车道，只挂只读检索工具

- 日期：2026-09-02
- 状态：已采纳

## 背景

用户拿 ChatGPT 对比速度：同样问"你了解过 51WORLD 这家公司吗"，那边几秒出答案，
我们这边要等半分钟以上。第一反应是"人家硬件强 / 思考步骤少"，实测下来两条都不是主因。

线上量的这一轮（生产 serve，openrouter + glm-5.3-flash）：

| 项 | 数字 |
|---|---|
| 整轮 | 35.5s |
| 其中模型往返 | **31.9s（90%）** |
| 其中工具执行 | 3.6s |
| 模型调用次数 | 5 次（4 个工具步 + 1 次收尾） |
| 累计 prompt | 26184 token，**缓存命中 0** |
| 单轮上下文构成 | system 3888 + **tools 8539** + messages 743 |

两件事跳出来：

1. **工具 schema 占了上下文的 65%**，而且每一步都完整重发。这一轮真正用到的工具是
   `web_search` 和 `web_images`，为它们俩陪跑的是另外 57 个。
2. **步数是冗余的**：`web_search` → `web_images` → `web_search` → `web_images`，
   同样的两个工具跑了两轮。

[ADR-0010](./0010-request-routing-lanes.md) 已经建立了 lane 机制，但当时只分了三条：`chat`
（寒暄，不挂工具）、`board`（板块任务，全量）、`work`（其余，全量）。知识型提问落在
`work`，于是拿到全套家伙去回答一个只需要"搜一下、翻翻知识库"的问题。

`chat` 那条道当时卡得极死是对的 —— 它的失败模式是**凭记忆瞎答**（ADR-0010 里记的反例
"新卖家注册身份验证失败怎么办"，一个业务词都不含，却是标准的知识库问题）。但正因为卡
得死，中间留下了一大片空白：既不是寒暄、也不需要动手的问题，全被推去走重载路线。

## 决定

新增第四条车道 `quick`：**知识型提问，照查不误，但只挂只读检索工具。**

- 工具集：`web_search` / `web_fetch` / `web_images` / `knowledge_search` / `recall` /
  `memory_search` / `memory_read` / `skill_search` / `skill_view`。9 个，约 1032 token
  —— 全量是 59 个、约 8296 token。
- 知识注入和引证**照旧**（这是它和 `chat` 的根本区别：`chat` 是不查，`quick` 是照查）。
- 关掉 todo / 阶段汇报状态机，跳过自动技能注入和工程上下文扫描 —— 一个知识问题没有
  阶段可分，也不需要一本 1600 字的运营手册。

判据分两层：先要命中知识提问的**形态**（"什么是 X"、"了解过 X 吗"、"X 和 Y 有什么区别"、
"X 是做什么的"…），再过三道闸 —— 工程词、动作词、**自有数据词**（"我的"、"店铺"、"报表"、
"最近"…）命中任意一个就退回 `work`。

**业务词故意不拦。** "ACOS 是什么意思"必须能走 quick —— 它要查的是那 83 张知识卡，而
`knowledge_search` 就在 quick 的工具集里。这正是 quick 存在的意义：`chat` 因为要防瞎答
而把整个业务知识域挡在门外，quick 把它接回来。

## 为什么 quick 可以比 chat 松

两条道判错的代价完全不同：

- `chat` 判错 = 不挂工具 = **凭记忆瞎答**。这是不可接受的，所以它必须整句白名单匹配。
- `quick` 判错 = 手上没有写工具 = 答案照样是查过才给的，只是这一轮动不了手。

所以 quick 的闸门只需要挡住"可能要动手"和"要看用户自己的数据"这两类，其余可以放行。
但方向仍然是**判不准回 work**：不是提问形态的一律不走，这一条没有松动。

## 同时修掉的一步冗余

`web_images` 现在把来源页的 `og:description` 一起带回来，并在结果里明说"这次调用拿到
的信息就够了，不用再 web_search"。摘要是白捡的 —— 抓 `og:image` 时 HTML 已经在手上，
描述就在旁边那一行。少这一段，模型就得为同一件事多走一次完整往返。

## 实测

**同一时刻交替跑，同一个问题，只换工具集**（交替是必须的：这条通道单次往返在
6~24 秒之间跳，单侧连跑得出的全是噪声）：

| 工具集 | 墙钟 | 模型往返 | prompt | 生成速度 |
|---|---|---|---|---|
| 全量 59 个 | 37.4s | 35.8s | 8461 tok | 46.9 ms/tok |
| **quick 9 个** | **26.3s** | 20.9s | 3039 tok | 29.0 ms/tok |
| 全量 59 个 | 78.1s | 75.9s | 17540 tok | 78.8 ms/tok |
| **quick 9 个** | **24.4s** | 18.4s | 3327 tok | 32.3 ms/tok |

两点值得记下来：

1. quick 不只是快，**方差也小得多**（26.3 / 24.4 对 37.4 / 78.1）。上下文越大，这条
   通道抖得越厉害。
2. 省 token 省的不止是"传输"：每 token 的**生成速度**也跟着快了一倍多（29~32 对
   47~79 ms/tok）。prompt 越长，注意力那一步越贵，这在长上下文里是复利。

生产 serve 上跑同一个问题，工具 schema 8539 → 929 tok、整轮 prompt 26184 → 11.1K、
工具步 4 → 2（三次跑步数稳定为 2）。serve 侧 prompt 比上面这张表高，是因为它还注入了
知识证据和会话历史 —— 那部分是要留的，quick 裁的从来只是工具。

## 影响与风险

- 收益见上表；工具步 4~5 → 2。
- 风险：形态判定误收一个其实要动手的问题 → 那一轮没有写工具。缓解是三道闸 + 默认
  回 `work`，且用例把"我的/店铺/报表/代码/配置"这些反例钉死了。
- `chat` / `board` / `work` 三条道的行为**一个字都没改**。
