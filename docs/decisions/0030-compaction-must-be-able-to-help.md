# ADR-0030：越过压缩阈值 ≠ 压得动

- 日期：2026-08-28
- 状态：已采纳

## 背景

自动压缩的判据一直只有一句：**用量越过阈值就压**
（`should_compact` / `should_compact_midturn` 拿 `compact_at_tokens` 比一比）。

这句话默认了一件没人写下来的事：压缩总能把用量降下去。它不总能。压缩只摘要历史，
**永远动不了 system 提示词**（`keep_system=True`），也不动保留区
（`compact_keep_recent`，默认 6 条原文）。所以只要 `compact_at_tokens` 被调到比
system 提示词本身还低 —— 换个小上下文模型时顺手调小、或者手滑填了个小数字 ——
用量就**永远**在阈值之上：

- 每一步都判定"该压了"；
- 每一次压缩都把还能直接用的近期原文换成一段散文摘要；
- 压完用量还在阈值之上，下一步接着压。

实测：20 个工具步里发生 10 次摘要调用，每次都是真花钱的模型调用，而历史被反复
摘要化 —— 净亏。这个坑一直在，只是从没被当成 bug 看：日志里它长得像"上下文
自动压缩，继续"，和正常压缩一模一样。

## 决策

**自动压缩多问一句："这次能压掉多少？"** 新增 `context.worth_compacting(messages)`：
按 `compact` 用的同一套切分算出待摘要段的 token 数，低于 `MIN_COMPACTIBLE_TOKENS`
（2000）就不跑。三个自动入口（`agent_loop._maybe_compact` 与 CLI 两处轮后压缩）
都加这道闸。

判据从"现在用了多少"改成"这次能压掉多少"。前者问的是紧不紧张，后者问的是压了有没有用；
只有后者能决定要不要花这次钱。

**手动 `/compact` 不受这道闸限制。** 用户敲下那一行就是明确要求，短历史也照压 ——
所以闸在调用方，不在 `compact()` 里面。

**挡下来要说一声。** `_maybe_compact` 在拦下时报一次（每轮至多一次），并直接给出
`config set compact_at_tokens <n>`。默不作声地忽略用户设的阈值，比压错更难查。

## 为什么不选另外两条路

**A. 把阈值自动抬到 system 之上。** 等于替用户改他的配置。而且 system 提示词的大小
随工具集、技能、注回的契约变，抬到多少都是猜；猜错就是另一种"设了不生效"。
报出来让人自己改，比替他改准。

**B. 在 `should_compact` 里减掉 system 的 token 再比阈值。** 这会悄悄改变
`compact_at_tokens` 的含义（从"总用量"变成"历史用量"），所有正常配置的会话压缩时机
都跟着变。这次要修的是一个边角失效，不该让所有人的行为跟着动。

## 代价与边界

- **多算一次估算**。`worth_compacting` 走 `estimate_tokens`，纯字符串统计，无模型调用。
- **2000 是个拍出来的数**。依据：摘要本身要花一次调用、产出约几百 token，压掉不到
  2000 token 的历史换不回这笔开销。没做成配置项 —— 又一个能被调错的旋钮，正是这次
  要修的病。
- **越过硬上限却压不动时，请求仍会溢出**。这种情况下 system 提示词自己就撑爆了窗口，
  压缩历史本来也救不了；区别只是现在不再白花一次调用，而且会明说原因。
