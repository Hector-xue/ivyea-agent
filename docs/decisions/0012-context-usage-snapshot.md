# ADR-0012 · 上下文用量由 serve 现算并上报，明说是估算

- **日期**：2026-08-18（v1.15.0 之后）
- **状态**：已采纳（已落地）
- **依据**：2026-08-18 会话；对标 DeepSeek Harness 的上下文进度条（见 [ADR-0008](./0008-borrow-from-deepseek-harness.md)）

## 背景

agentic 会话是**上下文先耗尽、再谈别的**：窗口一满就触发压缩，用户那边看到的症状是
"聊着聊着它开始忘事 / 突然变慢"。此前 serve 只在 `final.usage` 里回报服务商给的
`prompt_tokens`——它回答不了"我还剩多少"，因为：

- 它是"上一次调用花了多少"，会话刚开、本轮还没发出去时根本不存在；
- 它不带**窗口大小**，前端拿一个绝对值算不出百分比；
- 它是一个总数，说不清是谁吃掉的——而"该动哪里"完全取决于这个：系统提示词大
  = 人设/板块桥太长，工具大 = 挂了全量工具，对话消息大 = 该压缩历史了。

## 决策

serve 在两个时点发一份快照（`context.snapshot`）：`start` 之后、第一个 token 之前发
`context` 事件，收尾时再随 `final.context` 发一份。

```json
{"used": 9860, "window": 128000, "percent": 7.7,
 "breakdown": {"system": 1520, "tools": 6910, "messages": 1430},
 "estimated": true, "model": "deepseek-v4-pro"}
```

`used` 用 `context.estimate_tokens` 现算（CJK 0.75 token/字，其余 3.8 字/token），
工具那一档按本轮真实挂上的 schema 算（`tools=None` 表示全量，就按全量算）。
`window` 走 `context.window_for(model)`：一张模型→窗口的子串表，查不到落 128K 保守值，
`config set context_window` 可覆盖。

## 理由

**为什么不等服务商回报**：进度条要在这一轮发出去之前就说得出话，而服务商的数只在
回来之后才有。用估算换"第一时间就有"，是这条信息唯一能成立的方式。

**为什么必须带 `estimated: true`**：一个看起来精确、实际来路不明的数比一个标着"估算"的
数危险得多——用户会拿它当账算。前端据此在细账里写明"按字符估算，非服务商回报值"。
线上实测这套估算与 `prompt_tokens` 相差约 2%（1675 vs 1711）。

**为什么窗口查不到时给 128K 而不是编一个大的**：进度条报小了只是虚惊一场，报大了会让
人在真的快满时以为还早。

## 后果

- 老前端收到未知事件走自由文本兜底，`context` 事件不带 `text` 字段，落进去什么也不会
  渲染——不影响。老 agent 配新前端时进度条整块不出现，而不是画一个编的百分比。
- 模型窗口表需要跟着新模型维护。它只影响进度条的分母，错了不会影响任何执行路径。
