# ADR-0034：否词护栏放在自己这边，不动 vendor 进来的脚本

- 日期：2026-08-30
- 状态：已采纳

## 背景

`lingxing_optimizer.py`（领星 sid 维度规则引擎，**生产广告链路实际在用的那个**）的否词杠杆
是纯阈值：

```python
if m["clicks"] >= neg_clicks and m["orders"] == 0:   # 15 点击 0 单 → 否定
```

全文件 `brand|品牌|competitor|竞品` 命中数为 **0**。而沉淀下来的方法论明确写着「不能否：
品牌词、竞品词、战略大词、新品期差词、数据不足词、高转化低流量词、疑似 Listing 承接问题
而非流量问题的词」。品牌词天然就是"高点击、当期 0 单"的形态（品牌搜索常是比价或复购前的
浏览），正好落进这条规则里被否掉——**而否掉品牌词是直接掉销量的**。

需要澄清一件事：引擎并非没有护栏。`resolve_target_acos`（毛利率推目标 ACOS，0.7×毛利）、
`lingxing_bid_step_pct=15`、`lingxing_cooldown_days=7`、`_in_cooldown()`、`_rejected()`
历史否决都已经在。**缺的只是词性这一层。**

词分类能力其实**已经存在**，在 vendor 进来的 `rule_engine_scripts/analyze_search_term_decisions.py`
里（`detect_term_category` / `token_matches_any` / `is_asin_like_term`）。

## 决定

新建 `ivyea_agent/term_taxonomy.py`，只沿用那套**纯字符串**判定思路（分词 → 归一 → 编辑距离
相似 → 集合匹配），**不 import 那个脚本、也不改它**。护栏接在 `lingxing_optimizer` 现成的
`guard(name, kind) -> (ok, why)` 契约上，不改候选的既有字段。

判定分两档：

- **硬拦**（类别能确定的）：品牌词 / 战略词 / 竞品词（配置来的）/ 有转化的词 /
  CTR 远高于账户均值的词（流量是相关的，0 单更可能是承接问题 → 走 Listing 反馈）
- **放行 + 警告**（判不了的）：未配置品牌词、推断出来的疑似竞品词、ASIN 串号词、
  统计上还不够（按账户 CVR 算 0 单的概率）、经济上还不够（花费未超单笔毛利）

新增三个配置项 `lingxing_brand_tokens` / `lingxing_competitor_tokens` /
`lingxing_strategic_tokens`，**默认全空**。

## 理由

**为什么不改 vendored 脚本**：一来它 pandas 耦合，生产广告引擎这条路不该为了判断几个字符串
就把 pandas 拖进来；二来它硬编码了 `karaoke`/`videoke` 这类**特定类目**词表——整体搬进通用
引擎，等于把一个店铺的调参烙进所有店铺。三来改了就和上游分叉，以后没法跟。

**为什么默认空**：默认空 = 保持现有行为，只是候选上多一条"未配置品牌词"的警告。不静默改变
任何老用户已有的结果。

**为什么"判不了"要出警告而不是静默放行**：把不确定藏起来比拦错更糟。人工复核看不见的护栏
等于没有护栏。

**为什么推断出来的竞品词只警告、不硬拦**：推断噪音大。第一版实现漏了两条上限，实测直接把
`karaoke`、`machine` 这种品类词当成竞品品牌报出来——那种到处响的警告只会训练人忽略警告，
比不出警告更糟。补了"出现比例上限 15%"和"样本少于 30 条不推断"两道闸。

**为什么风险取舍是"宁可少否"**：拦错一个该否的词，代价是这一轮少省一点无效花费；放过一个
品牌词，代价是把自己的品牌搜索流量掐掉。不对称，所以拿不准一律不否，并说明拿不准在哪。

## 后果

- 顺带修掉一处会让护栏**静默失效**的实现问题：第一版只做单 token 匹配，而真实配置里
  "anker soundcore"、"karaoke machine" 这类多词品牌很常见，它们永远不等于任何一个单 token
  ——配了等于没配，用户还以为护栏开着。现在单词和多词短语都认。
- 「新品期差词」这条护栏**没有覆盖**：需要商品上架时间，领星广告数据面当前取不到。
  在报告里明文列进"护栏未覆盖项"，不让人误以为全覆盖了。
- 顺手对齐了三处互相矛盾的护栏数字：代码是 15% 步长 / 7 天冷却，而 `knowledge.py` 的
  METHODOLOGY 提示词写的是 20% / 5 天、`playbooks/budget_bid_scaling.md` 写的是 10-20%。
  以代码为准统一，并在提示词里标明这是本系统的运营口径、不是亚马逊官方规则。
- 教训：**方法论落在提示词里不等于落地**。同一套数字散在提示词、playbook、代码三处会各自
  漂移，而只有代码那份是真正执行的。以后新增阈值先问"谁在执行它"。
