# ADR-0004 · 完成前自验证门禁

- **日期**：2026-07-05（v1.3.0）
- **状态**：已采纳
- **依据**：提交 `feat(agent): 思考深度旋钮 + 完成前自验证门禁 + 通用自我批判 + 多轮修复`；
  相关会话 2026-07-05 Codex

## 背景

一次具体的失望触发了这个决定。作者检查 agent 刚跑完的任务，发现两件事：

1. 它报告任务完成，但实际没做对
2. 「在识别分析理解指令上面有些欠缺，因为我刚才那个指令，他找了好久才定位到应该修改哪些文件」

也就是说，**理解**和**执行**两端都有问题，而「报告完成」这个动作本身没有任何门槛 —— 模型
说完了就是完了。

## 决策

在 agent 声明完成之前插一道门禁：

- **完成前自验证** —— 必须实际验证改动成立（跑测试、读回文件、执行命令），不能只凭"我改了"
- **通用自我批判** —— 完成前对自己的产出过一遍，找出不足
- **多轮修复** —— 自验证发现问题就继续修，而不是把问题报给用户
- **思考深度旋钮** —— 让调用方能按任务难度调节推理投入

## 理由

- 「说完成了」和「真的完成了」之间的差距，是 AI 编码最大的隐性成本 —— 用户要花时间发现它
- 自验证的成本远低于用户发现问题后返工的成本
- 这条与 IvyeaOps 侧的五步开发流是同一个思路的两端：五步流管**动手前**，自验证门禁管
  **收工前**

## 后果

- 成为此后所有任务的默认行为
- 派生纪律：**声明完成前必须自检消费方** —— 改了契约就要检查所有调用它的地方，
  这一条在 Sorftime 参数名、stream 信封、版本源等多次事故里都是根因
