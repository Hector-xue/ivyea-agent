# ADR-0027：思考按轮定档、自查由运行时兜底、证据要落盘

- 日期：2026-08-28
- 状态：已采纳

## 背景

[ADR-0026](./0026-the-plan-is-runtime-state.md) 把**计划**从"模型自己记得"改成了运行时状态。
同一类问题在"思考 / 自查 / 证据"这三处还各留了一份：

1. **思考深度是全局静态的**。`reasoning_effort` 默认 `high`，一句"好的"和一次跨仓重构
   按同样深度去想。而 `routing.py` 早就把每轮判成了 chat / board / work 三条路线 ——
   那份判断只用来决定挂不挂工具，没人拿它调思考深度。
2. **自查全靠模型自觉**。`self_critique` 工具在，但要不要调、什么时候调，全由模型自己定。
   "该自查的时候自查"交给自觉，等于没有 —— 而恰恰是动过代码、下过写指令的那些轮次，
   返工代价最高。
3. **"证明过什么"活不过这一轮**。`progress_tool_evidence` 只在 `progress_required` 的
   轮次收集，且挂在 `ToolContext` 上，换一轮就没了。于是"上次我们验证过什么"永远答不上来，
   最终汇报的「验证」一栏在普通轮里只能靠模型自述。

## 决策

### 1. 新增 `adaptive` 档，不动 `auto`

`auto` **已经有明确含义了，而且各家不一样**：Gemini 映射成 `thinkingBudget: -1`（动态思考，
模型自己决定预算），其余几家映射成"不传思考参数、用模型默认"。把 `auto` 改成"自适应"
会悄悄改掉所有显式设过 `auto` 的人的行为 —— 而他们当初选它，正是为了"交给模型自己定"。
所以另开一档 `adaptive`。

映射刻意保守：**唯一被调低的是寒暄**（chat → low，这条路线本来就连工具都不挂），
board / work 一律维持 `high`；带 `progress_required` 或 `execution_expected` 的多步执行
无论哪条路线都强制 `high`。

**默认仍是 `high`。** 不做任何设置的老用户行为逐字不变 —— 思考深度直接影响回答质量，
不能因为"我觉得这样更省"就替用户降档。

落点在每轮开始时改 `provider.reasoning_effort`，**不是** `from_settings`：provider
每个会话只构造一次，挂在构造那一步等于还是全局静态。

### 2. 自查升级为收尾门禁，但只盯"动过东西"的轮次

新增 `_critique_gate_feedback`，排在 verify / progress / citation 之后、同一条收尾链上。

触发面刻意收窄到两种：**改过真代码文件**（`wrote_code_files`，与行为门禁同一条判据，
只写 `.md` 不算）或**真下过写指令**（广告 `execute_actions` / 领星写回实际执行成功）。
理由是自查要多花一次模型调用，全轮次开等于给每次问答加一份税；而这两种轮次改错了要再改
一遍、下错了要花钱，是返工代价最高的地方。

配套三条：

- **rubric 分域**（code / ads / knowledge / general）。一份通用 rubric 覆盖不了差异：
  代码要问"验证过没有、消费方契约动了没有"，广告要问"数据够不够、护栏越没越"，
  知识要问"这是官方事实还是你的推断"。
- **模型自己调过 `self_critique` 就不代劳**。
- **拿不准一律放行**。误判成"要修"的代价是白跑一轮、甚至逼模型改坏已经对的答案；
  误判成"通过"只是这次没帮上忙。方向不对称，所以 `needs_fix` 只认结论行、
  同时出现"通过"就算过。封顶 1 轮。

### 3. 证据台账独立落盘

新增 `evidence_ledger`（`~/.ivyea/evidence.db`），在 `_record_tool_result` 里被动记录
命令 / 测试 / 读 / 写 / 接口五类有验证意义的调用，跨轮跨会话可查，30 天过期。
最终汇报的「验证」一栏把它作为最后一档兜底 —— 前三档（模型自述、阶段报告、本轮工具痕迹）
都活在这一轮的内存里，台账是唯一落了盘、能事后对账的那份。

**它是被动的**：只记录发生过什么，不判断够不够、不拦任何人。判断留给门禁。

## 为什么不选另外几条路

**A. 把 `auto` 重新定义成自适应。** 见上，会破坏 Gemini 的动态思考预算和其他几家的
"用模型默认"语义，而且改的是别人显式做过的选择。

**B. 自查做成每轮都跑。** 每次问答加一次模型调用，成本和尾延迟翻倍，而绝大多数轮次
根本没有东西可返工。收窄触发面拿到了大部分收益、付了很小的代价。

**C. 证据挤进 `traces.db`。** traces 是给运行时间线 UI 看的全量流水，保留策略和查询
形状都不一样；证据台账要按类别查、要能过期清理。两件事塞一张表迟早互相掣肘。

## 代价与边界

- **自查会让"改过代码的那一轮"多一次模型调用**，收尾前会看到一行"改动已落盘，交付前先
  自查一遍…"。可用 `critique_before_done=false` 关掉。
- **多一个数据库文件**。写失败一律吞掉（照抄 `traces.py` 的做法），台账坏了不连累干活。
- **`adaptive` 是显式选项，不开就完全不存在。** 这是有意的保守：真正省钱的是少走步数
  （见 [ADR-0010](./0010-request-routing-lanes.md)），不是把思考调低。
- 台账**不判断**证据够不够。"没证据就不许说完成"那条判断留在 `progress_reporting`
  的阶段门禁里，两边职责不混。
