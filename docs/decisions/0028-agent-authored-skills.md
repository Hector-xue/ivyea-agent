# ADR-0028：技能改成 agent 自己能读全、能写、能沉淀

- 日期：2026-08-28
- 状态：已采纳

## 背景

技能系统此前是**只读的，而且读不全**。

1. **模型手上只有 `skill_search` 一个工具。** 它可以刚刚走完一套完整的领星广告巡检流程，
   然后眼睁睁看着这套流程随会话消失 —— 建技能必须人去敲 `ivyea skill create`。
2. **自动注入把正文截到 700 字，而剩下的部分模型根本够不着。** 没有任何工具能读技能全文。
   于是一本三千字的审计手册，模型永远只看得到开头那段"何时使用"，真正的步骤和护栏全在
   截断线以下 —— 它照着残缺的手册干活，还以为自己看全了。附属文件（`references/`、
   `scripts/`）同理。
3. **检索是纯词法 2-gram + 一张手工停用词表。** `skills.py` 的 `_STOP_GRAMS` 上面记着那次
   真实事故：「为什么我的模型配置页面报错」以 22 分命中 ASIN 审计手册。反过来也一样 ——
   口语化问法和技能里的正式用词对不上，词法就是零命中。而 `memory_vectors.hybrid_rank`
   （RRF 双路召回，记忆那边已经验证过）就在同一个仓里，没被技能用上。
4. **没有使用统计**，于是"哪条技能是死的""哪两条重复了"只能靠拍脑袋 —— 技能库已经近百条。

## 决策

### 1. 补两个工具：`skill_view`（只读）与 `skill_write`（写，走审批）

`skill_view` 读技能全文，或读目录下的 `references/` / `scripts/` / `templates/`。
配套把自动注入改成**开头一段 + "要全文用 `skill_view`"**：截断本身没变（上下文是有价的），
变的是**截掉的部分现在拿得回来**。

`skill_write` 支持 write / write_file / archive。`skill_view` 进 `READONLY_TOOLS`
（子 agent 可以读），`skill_write` **不进** —— 子 agent 的一次探索不足以决定
"这值得沉淀成技能"，那是主线的判断。

### 2. 作者规范写成**代码**，不是写进 prompt

hermes 把整套规范塞进 `/learn` 的 prompt 里指望模型照做。它自己在注释里承认，那份规范里
最要紧的一条是"最常被违反的规则"—— 因为没有人检查。**规范只要不可执行，就一定会慢慢烂掉。**

所以 `skill_authoring.validate` 在落盘前当场判定，不过就不写。

**规则只从本仓真实存在的约束里来。** hermes 要求 description ≤ 60 字符，理由是它的技能索引
按 60 字截断；ivyea **没有这个截断**（`render_list` 打全文、`_score_parts` 也吃全文），
照搬这个数字就是 cargo cult。换成有依据的两条：

- **`triggers` 必填（硬错误）** —— `_terms()` 不分词，中文查询几乎完全靠触发词作为子串命中
  （`skills.py` 自己的注释就是这么写的）。没有触发词的技能，中文用户根本搜不到它。
- **description 只给宽松上限 + 建议值** —— 它进匹配范围，但 `_META_HIT_CAP=3` 已经封顶：
  写成一大段不会更容易命中，只会稀释。

"不许发明命令"落成可检查的版本：正文里 backtick 引的、带 `skill_`/`run_`/`mcp_` 这类前缀
但不在 `TOOL_SCHEMAS` 里的名字 → 警告。只对**看起来像我们工具**的词报警，否则满篇变量名全是误报。

### 3. `/learn` 编译成一轮指令，不再造引擎

学技能需要的能力 agent 全都有：`glob`/`read_file` 读目录、`web_fetch` 抓网页、
"刚才那件事"就在会话里、`skill_write` 落盘。`learn_prompt` 只产出**一段指令**，
交给当前会话按正常一轮跑掉 —— CLI（`/learn`、`ivyea learn`）、serve、飞书三个入口自动都有了。

大素材走知识库布局（精简 SKILL.md 索引 + `references/` 分章，**一章一写**）。这不是排版偏好：
把一本书塞进一次对话会直接撑爆上下文，而摘要式压缩会把结构（决策规则、阈值表、反模式）压没 ——
那些恰恰是唯一值得留下的东西。

**素材是数据不是指令**的防护每次都嵌进去：`web_fetch` 抓回来的亚马逊政策页、第三方文档是
注入的日常入口。

### 4. 语义层接上，但**不进注入路径**

`skills.search` 接 `memory_vectors.hybrid_rank`（RRF），两条纪律：

- **候选集是全部技能，不是词法命中的那些。** 把语义做成"重排词法候选"是错的 —— 词法零命中时
  候选集是空的，语义根本没有机会，而那正是它唯一存在的理由（`vector_recall` 的注释记着这个坑）。
- **自动注入（`named_only=True`）那道闸不因语义放松，`recall` 的技能指针直接 `semantic=False`。**
  几十条技能是个小语料，余弦**永远**返回"最像的那几条"，没有"都不像"这个答案。实测：
  「完全不存在的东西」也能匹配出三条技能 —— 那正是那次老事故的语义版。
  按语义找技能是 `skill_search` 的事，那时候用户在主动翻库。

配套给 `ivyea eval` 补了技能召回 golden set，**反例和正例一起进**：5 条该命中的 +
5 条自动注入一条都不该命中的（含事故原句）。一条正例测不出检索质量 —— 改检索最容易出的事故
不是"该召的没召"，是"不该召的召了"。

### 5. 使用统计 + 归档

`skill_usage` 记命中次数/最近命中/命中来源，落 `~/.ivyea/skills/usage.json`。
`ivyea skill usage` 看，`archive` / `restore` 管生命周期 —— **只归档不删除**。

## 落地时打出来的三个真 bug

都是写完测试才发现的，值得记下来：

1. **写进去的 id 和加载回来的 id 对不上。** 加载器没有 `id` 字段就从 `name` 推导
   （`skills._slug`），于是 `name: lingxing-ad-patrol` 被推成 `id: lingxing.lingxing_ad_patrol`。
   后续 `skill_view` / `archive` 按原 id 全找不着。修法：`write_user_skill` 把 `id` 显式写进
   frontmatter。
2. **归档等于没归档。** `_archive/` 是 `~/.ivyea/skills/` 的子目录，扫描器照样把它当技能加载。
   修法：`_iter_root` 显式跳过。
3. **语义层泄进了注入路径**（见上）。

## 代价与边界

- **多了一条 agent 能写的路径。** 写操作照旧走审批，计划模式一律拒绝；校验闸挡住半成品。
- **`skill_write` 不给子 agent。** 保守，但沉淀技能是长期决定，不该由一次探索做主。
- **语义层默认开**（`skill_semantic_search`），因为随包的 bge-small-zh 是零配置的；
  没有 dense 后端时行为与纯词法**逐条相同**。
- **归档只对用户自建技能生效**，内置技能不许归档 —— 它们随包发布，归档了下次升级又回来。
